# 上线自检清单

> 适用范围：单商户跨境商城（9 个容器：postgres / redis / pgbouncer / api / worker / storefront / admin / nginx / migrator），Docker Compose 部署。
> 判定口径：本清单的每一项都必须留下「命令输出」或「截图/日志」作为放行证据；任何 FAIL 项未关闭，不得放行生产流量。
> 维度映射：各章节标题后的括号标注了 `production-readiness-scorecard.md`（`references/01-standards/`）对应的记分卡维度。

---

## 0. 使用方式

### 0.1 三条命令先跑一遍

```bash
# 1) 自动化诊断（覆盖环境/容器/数据库/缓存/密钥/备份/HTTP 七类）
bash deploy/scripts/doctor.sh

# 2) 健康检查（容器状态 + 健康端点）
bash deploy/healthcheck.sh

# 3) 交易闭环回归（建车 → 加购 → 运费 → 结账 → 授权 → 扣款 → 订单转正 → 发货）
bash deploy/scripts/e2e-regression.sh
```

`doctor.sh` 的退出码：`0` = 无 FAIL（可能有 WARN）；`1` = 有 FAIL。FAIL 项会直接给出可复制执行的处置命令。

### 0.2 判定规则

| 标记 | 含义 | 放行要求 |
|------|------|----------|
| OK | 检查通过 | — |
| WARN | 有风险但不阻断 | 记入遗留项，写明责任人与期限 |
| FAIL | 必须修复 | 未关闭不得放行 |

### 0.3 环境变量约定

下列命令默认在**目标服务器**上、以 `root` 或 `mall` 用户执行，且已 `cd` 到程序目录（`MALL_DIR/app`，默认 `/opt/mall/app`）。所有脚本均可用 `MALL_DIR=<路径>` 覆盖。

```bash
export MALL_DIR=/opt/mall
cd $MALL_DIR/app
```

## 1. 环境（记分卡维度：发布安全）

- [ ] **1.1 主机资源满足最低门槛**
  - 命令：`free -m && nproc && df -h $MALL_DIR`
  - 通过标准：内存总量 ≥ 2G（可用 ≥ 512M）、CPU ≥ 2 核、`$MALL_DIR` 所在分区剩余 ≥ 20%
  - 失败处置：`sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile`；清理磁盘 `docker system prune -af --volumes=false`

- [ ] **1.2 Docker 与 Compose 可用**
  - 命令：`docker --version && docker compose version && docker info | head -5`
  - 通过标准：Docker ≥ 24、Compose v2 可用、`docker info` 正常输出 Server 信息
  - 失败处置：`curl -fsSL https://get.docker.com | sh && sudo systemctl enable --now docker`；`sudo apt-get install -y docker-compose-plugin`

- [ ] **1.3 9 个容器全部在跑且健康**
  - 命令：`docker compose --env-file $MALL_DIR/config/.env ps`
  - 通过标准：`postgres / redis / pgbouncer / api` 状态为 `healthy`；`worker / storefront / admin / nginx` 状态为 `running`；`migrator` 显示 `Exited (0)`（一次性任务，正常退出）
  - 失败处置：`docker compose --env-file $MALL_DIR/config/.env logs --tail 100 <服务名>` 看日志；`docker compose --env-file $MALL_DIR/config/.env up -d <服务名>` 重拉

- [ ] **1.4 容器没有崩溃循环**
  - 命令：`for c in $(docker compose --env-file $MALL_DIR/config/.env ps -q); do echo "$c $(docker inspect -f '{{.RestartCount}}' $c)"; done`
  - 通过标准：每个容器 `RestartCount` ≤ 3
  - 失败处置：`docker compose --env-file $MALL_DIR/config/.env logs --tail 200 <服务名>`；若为 OOM：`docker stats --no-stream` 与 `dmesg -T | grep -i 'killed process'`

- [ ] **1.5 nginx 配置语法正确**
  - 命令：`docker compose --env-file $MALL_DIR/config/.env exec -T nginx nginx -t`
  - 通过标准：输出 `syntax is ok` / `test is successful`，退出码 0
  - 失败处置：`docker compose --env-file $MALL_DIR/config/.env exec -T nginx nginx -t` 看具体报错行；改 `deploy/docker/nginx.conf` 后必须显式 `exec -T nginx nginx -s reload`（bind mount 不会自动重载）

- [ ] **1.6 程序与数据分离（拓扑铁律）**
  - 命令：`ls -la $MALL_DIR && ls $MALL_DIR/config && ls $MALL_DIR/data`
  - 通过标准：`.env` / `secrets.json` 只在 `$MALL_DIR/config/`；`pgdata` / `uploads` / `backup` 只在 `$MALL_DIR/data/`；替换 `app/` 目录不触碰这两处
  - 失败处置：把散落的配置/数据移回 `$MALL_DIR/config` 与 `$MALL_DIR/data`，并核对 `docker-compose.yml` 里的 `${MALL_DIR}` 挂载路径

## 2. 密钥与配置（记分卡维度：安全）

- [ ] **2.1 `.env` 存在且权限收敛**
  - 命令：`ls -l $MALL_DIR/config/.env && stat -c '%a' $MALL_DIR/config/.env`
  - 通过标准：文件存在，权限为 `600`
  - 失败处置：`chmod 600 $MALL_DIR/config/.env`

- [ ] **2.2 `secrets.json` 存在且权限收敛**
  - 命令：`ls -l $MALL_DIR/config/secrets.json && stat -c '%a' $MALL_DIR/config/secrets.json`
  - 通过标准：文件存在，权限为 `600`
  - 失败处置：`chmod 600 $MALL_DIR/config/secrets.json`；缺失则从 `.env` 复制一份留存：`cp $MALL_DIR/config/.env $MALL_DIR/config/secrets.json && chmod 600 $MALL_DIR/config/secrets.json`

- [ ] **2.3 三个关键密钥都不是 dev 默认值**
  - 命令：`grep -E '^(JWT_SECRET|ENCRYPTION_KEY|POSTGRES_PASSWORD)=' $MALL_DIR/config/.env | sed 's/=.*/=<已设置，值已隐藏>/'`
  - 通过标准：三个键都存在，且值不等于 `dev-jwt-secret` / `dev-encryption-key` / `mall`；长度分别 ≥ 32 / 32 / 16
  - 失败处置：`sed -i 's|^JWT_SECRET=.*|JWT_SECRET='"$(openssl rand -hex 32)"'|' $MALL_DIR/config/.env`，三个密钥分别替换后执行 `docker compose --env-file $MALL_DIR/config/.env up -d --force-recreate api worker pgbouncer`
  - 说明：本项目真实故障是 `.env` 随源码丢失 → 容器 fallback 到 compose 里的 dev 默认密码 → 认证失败。`doctor.sh` 的 `secret.*` 与 `runtime.*` 两组检查专门盯这条

- [ ] **2.4 容器内实际生效的密钥与 `.env` 一致**
  - 命令：`docker compose --env-file $MALL_DIR/config/.env exec -T api printenv JWT_SECRET | md5sum && grep '^JWT_SECRET=' $MALL_DIR/config/.env | cut -d= -f2- | tr -d '\n' | md5sum`
  - 通过标准：两个 md5 相同（说明容器是按当前 `.env` 重建的）
  - 失败处置：`docker compose --env-file $MALL_DIR/config/.env up -d --force-recreate api worker`

- [ ] **2.5 `.env` 里的数据库口令能真正认证**
  - 命令：`docker compose --env-file $MALL_DIR/config/.env exec -T -e PGPASSWORD="$(grep '^POSTGRES_PASSWORD=' $MALL_DIR/config/.env | cut -d= -f2-)" postgres psql -h 127.0.0.1 -U mall -d mall -tAc 'SELECT 1'`
  - 通过标准：输出 `1`
  - 失败处置：从 `secrets.json` 取回原口令写回 `.env` 后 `docker compose --env-file $MALL_DIR/config/.env up -d --force-recreate pgbouncer api worker`

- [ ] **2.6 CORS 不再是全放行**
  - 命令：`grep '^CORS_ORIGINS=' $MALL_DIR/config/.env`
  - 通过标准：值是具体域名列表；同源部署（店面/后台都经 nginx 反代）留空即可，但**绝不能是 `*`** —— 后端把它当字面量白名单，`*` 既不表示「放行所有」也会误导运维
  - 失败处置：`sed -i 's|^CORS_ORIGINS=.*|CORS_ORIGINS=https://你的域名|' $MALL_DIR/config/.env` 后 `docker compose --env-file $MALL_DIR/config/.env up -d --force-recreate api worker`

- [ ] **2.7 管理端默认口令已改掉**
  - 命令：`curl -s -X POST http://127.0.0.1/api/v1/admin/auth/login -H 'Content-Type: application/json' -d '{"email":"admin","password":"123456"}'`
  - 通过标准：响应里**没有** `access_token`
  - 失败处置：首选用后台改密页改密，或调改密端点（需管理员 access_token，改密后需重新登录）：
    ```bash
    curl -s -X POST http://127.0.0.1/api/v1/admin/auth/change-password \
      -H "Authorization: Bearer <管理员 access_token>" -H 'Content-Type: application/json' \
      -d '{"current_password":"<当前口令>","new_password":"<至少8位且含字母与数字>"}'
    ```
    仅在忘记口令 / 账号被锁时才用应急兜底：`bash deploy/scripts/set-admin-password.sh --generate`
    —— 该脚本走 DB 层轮转（软删旧 identity + admin_user 再由 seed 重建），**会导致 `admin_user.id` 变化**，角色绑定与审计里的 `actor_id` 会跟着漂；能用改密端点就别用它
    恢复出厂默认口令（降级操作）：`bash deploy/scripts/set-admin-password.sh --restore-default --yes`
    —— 出厂默认口令 `123456` 不满足强度规则（6 位纯数字），所以这条路径**刻意绕过强度校验**；没有它就会「一改密就再也回不去」。恢复后口令是弱口令，**必须立刻用后台改密页改成强口令**。同样会让 `admin_user.id` 变化

## 3. 数据库（记分卡维度：契约 / 发布安全）

- [ ] **3.1 数据库连通且版本符合预期**
  - 命令：`docker compose --env-file $MALL_DIR/config/.env exec -T postgres psql -U mall -d mall -tAc 'SELECT version()'`
  - 通过标准：返回 `PostgreSQL 18.x ... on x86_64-pc-linux-gnu`
  - 失败处置：`docker compose --env-file $MALL_DIR/config/.env logs --tail 50 postgres`；`docker compose --env-file $MALL_DIR/config/.env restart postgres`

- [ ] **3.2 迁移已全部应用（与程序版本一致）**
  - 命令：`docker compose --env-file $MALL_DIR/config/.env exec -T postgres psql -U mall -d mall -tAc 'SELECT count(*) FROM schema_migrations'` 与 `ls $MALL_DIR/app/packages/*/migrations/*.sql | wc -l`
  - 通过标准：两个数字相等；且 `SELECT name FROM schema_migrations ORDER BY name DESC LIMIT 1` 与磁盘上按名排序最大的迁移文件一致
  - 失败处置：`docker compose --env-file $MALL_DIR/config/.env run --rm migrator`
  - 说明：迁移**只增不删**，破坏性变更由 `pnpm check:migrations`（AST lint）拦截

- [ ] **3.3 表结构与契约文档一致**
  - 命令：`docker compose --env-file $MALL_DIR/config/.env exec -T postgres psql -U mall -d mall -tAc "SELECT count(*) FROM information_schema.tables WHERE table_schema='public'"`
  - 通过标准：表数量与 `docs/04-specs/db-schema.md` 记录的 76 张表口径一致（允许有内部辅助表）
  - 失败处置：核对 `schema_migrations` 是否全部应用；差异大说明代码与数据库版本不匹配，走回滚流程（第 10 节）

- [ ] **3.4 连接数未逼近上限**
  - 命令：`docker compose --env-file $MALL_DIR/config/.env exec -T postgres psql -U mall -d mall -tAc 'SELECT count(*) FROM pg_stat_activity'` 与 `SHOW max_connections`
  - 通过标准：使用率 < 80%
  - 失败处置：查连接来源：`SELECT state,count(*) FROM pg_stat_activity GROUP BY state`；确认是 pgbouncer 连接池参数偏小还是有连接泄漏

- [ ] **3.5 参数按机器规格调过（不是默认值）**
  - 命令：`cat $MALL_DIR/config/tuning.env && docker compose --env-file $MALL_DIR/config/.env exec -T postgres psql -U mall -d mall -tAc 'SHOW shared_buffers'`
  - 通过标准：`tuning.env` 存在，`TIER` 与机器内存匹配，`shared_buffers` 生效值与 `tuning.env` 一致
  - 失败处置：`MALL_DIR=$MALL_DIR bash deploy/scripts/tuning.sh` 后 `docker compose --env-file $MALL_DIR/config/.env restart postgres`

- [ ] **4.3 队列没有积压、没有失败任务**
  - 命令：`docker compose --env-file $MALL_DIR/config/.env exec -T redis redis-cli --scan --pattern 'bull:*:wait'`

  - 失败处置：确认 worker 在跑：`docker compose --env-file $MALL_DIR/config/.env ps worker`；`docker compose --env-file $MALL_DIR/config/.env logs --tail 100 worker`；查看失败原因 `redis-cli LRANGE bull:payment-webhook:failed 0 -1`

- [ ] **4.4 Redis 持久化开启**
  - 命令：`docker compose --env-file $MALL_DIR/config/.env exec -T redis redis-cli CONFIG GET appendonly`
  - 通过标准：返回 `appendonly` / `yes`
  - 失败处置：`docker compose --env-file $MALL_DIR/config/.env exec -T redis redis-cli CONFIG SET appendonly yes`，并把 `appendonly yes` 固化进 `$MALL_DIR/config/redis.conf`

- [ ] **5.2 API 健康端点五项全绿**
  - 命令：`curl -s http://127.0.0.1/api/v1/health`
  - 通过标准：`{"code":0,"data":{"status":"ok","db":"ok","redis":"ok","queue":"ok","migrations":"..."}}`
  - 失败处置：按降级项定位——`db` 看第 3 节、`redis`/`queue` 看第 4 节、`migrations` 看 3.2

- [ ] **5.3 域名解析指向本机**
  - 命令：`getent hosts 你的域名 && curl -s https://api.ipify.org`
  - 通过标准：两者 IP 一致（NAT / CDN 场景例外，但必须确认流量确实到达本机）
  - 失败处置：修正域名的 A 记录；签发证书前可用 `bash deploy/scripts/setup-https.sh --skip-dns-check` 绕过校验

- [ ] **5.4 HTTPS 证书已签发且未过期**
  - 命令：`docker run --rm -v $MALL_DIR/config/letsencrypt:/etc/letsencrypt certbot/certbot certificates`
  - 通过标准：存在 `Certificate Name: 你的域名`，`Expiry Date` 距今 > 30 天
  - 失败处置：`bash deploy/scripts/setup-https.sh --domain 你的域名 --email 运维邮箱 --install-cron`

- [ ] **5.5 HTTPS 响应带 HSTS，HTTP 响应不带**
  - 命令：`curl -sI https://你的域名/ | grep -i strict-transport-security` 与 `curl -sI http://你的域名/ | grep -i strict-transport-security`
  - 通过标准：HTTPS 响应有 `Strict-Transport-Security`，HTTP 响应**没有**
  - 失败处置：检查 `$MALL_DIR/config/nginx/https.inc` 是否生成、是否 `docker compose --env-file $MALL_DIR/config/.env exec -T nginx nginx -s reload`

- [ ] **5.6 证书自动续期已安装**
  - 命令：`crontab -l | grep mall-https-renew`
  - 通过标准：存在一行 `0 3 * * * ... certbot renew ... --deploy-hook ... nginx -s reload`
  - 失败处置：`bash deploy/scripts/setup-https.sh --domain 你的域名 --email 运维邮箱 --install-cron`；或手工验证续期 `bash deploy/scripts/setup-https.sh --renew`

- [ ] **5.7 80 → 443 跳转策略符合预期**
  - 命令：`curl -sI http://你的域名/ | head -3`
  - 通过标准：默认（未加 `--force-https`）返回 `200`（HTTP 仍可访问）；启用强制跳转后返回 `301` 且 `Location` 为 `https://` 开头
  - 失败处置：收紧跳转 `bash deploy/scripts/setup-https.sh --domain 你的域名 --email 运维邮箱 --force-https`；或回退 `bash deploy/scripts/setup-https.sh --disable`

- [ ] **5.8 80 端口的 ACME 校验目录没被跳转拦截**
  - 命令：`echo test-token > $MALL_DIR/config/certbot-webroot/.well-known/acme-challenge/test && curl -s http://你的域名/.well-known/acme-challenge/test`
  - 通过标准：返回 `test-token`
  - 失败处置：确认 `deploy/docker/nginx.conf` 里存在 `location /.well-known/acme-challenge/`，且 `https.inc` 的 80 跳转块里也保留了同一条 location；改完 `nginx -s reload`

## 6. 安全（记分卡维度：安全）

- [ ] **6.1 管理端接口需要鉴权**
  - 命令：`curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1/api/v1/admin/orders`
  - 通过标准：返回 `401`（未带 token 不得返回数据）
  - 失败处置：核对 `apps/api` 的鉴权中间件与 RBAC 角色配置；变更前先在测试环境验证

- [ ] **6.2 后端安全响应头已下发**
  - 命令：`curl -sI http://127.0.0.1/api/v1/health | grep -iE 'x-content-type-options|x-frame-options|referrer-policy'`
  - 通过标准：三个头都存在
  - 失败处置：确认后端 `HTTPS_ENABLED` / 安全头配置项已开启，并重启 `api` 容器

- [ ] **6.3 请求体大小受限**
  - 命令：`curl -s -o /dev/null -w '%{http_code}\n' -X POST http://127.0.0.1/api/v1/store/carts -H 'Content-Type: application/json' -d "$(head -c 30000000 /dev/zero | tr '\0' 'a')"`
  - 通过标准：返回 `413`（不是 `500`）
  - 失败处置：确认 `client_max_body_size` 与后端 body limit 配置一致；nginx 侧改 `deploy/docker/nginx.conf` 后必须 `nginx -s reload`

- [ ] **6.4 管理后台入口路径正确（`/admin/` 前缀剥离未回归）**
  - 命令：`curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1/admin/ && curl -s http://127.0.0.1/admin/ | head -c 200`
  - 通过标准：返回 `200` 且是后台页面 HTML（不是 404、不是店面页）
  - 失败处置：确认 `deploy/docker/nginx.conf` 里 `location /admin/` 的 `rewrite ^/admin/(.*)$ /$1 break;` 还在；改完 `nginx -s reload`

- [ ] **6.5 上游是动态解析（容器换 IP 不 502）**
  - 命令：`docker compose --env-file $MALL_DIR/config/.env exec -T nginx getent hosts api`
  - 通过标准：能解析出当前 api 容器 IP；且 `nginx.conf` 里是 `resolver 127.0.0.11` + `set $api_upstream` 的变量写法
  - 失败处置：若配置退化成了静态 `proxy_pass http://api:3000`，改回变量写法并 `nginx -s reload`（真机问题 #28 的回归症状就是全站 502 而 nginx 毫无察觉）

- [ ] **6.6 没有把密钥写进源码或镜像**
