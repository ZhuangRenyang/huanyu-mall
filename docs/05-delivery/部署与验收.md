## 1. 一句话结论

`bash deploy/install.sh` 一条命令，在干净 Debian 13 上**10 步全绿**装完并跑通交易闭环。过程中暴露并修复了 **27 个只在真机才现形的问题**（含 3 个「代码看着对、实际是空白页/构建失败」级别的缺陷）——这正是「干净机器实测」这条验收标准的价值所在。

## 2. 系统构成

9 个容器（`docker-compose.yml`）：

| 服务 | 作用 | 端口 |
|---|---|---|
| `nginx` | 统一入口： `/api/*`→api，`/admin/*`→admin，其余→storefront | `${HTTP_PORT:-80}` |
| `api` | Fastify 5 + Store/Admin API（41 端点） | 内部 3000 |
| `worker` | BullMQ 消费者（队列 / 死信） | — |
| `storefront` | Next.js 16 店面（PC + H5 同一套响应式代码） | 内部 3000 |
| `admin` | React 19 + Vite 管理后台（静态站，nginx 托管） | 内部 80 |
| `migrator` | 一次性迁移执行器（19 个迁移文件） | — |
| `postgres` | PostgreSQL 18 | 内部 5432 |
| `redis` | Redis 8.10（缓存 / 事件 / 队列） | 内部 6379 |
| `pgbouncer` | 连接池（session 模式） | 内部 6432 |

**数据与程序隔离**（铁律 10）：程序在 `/opt/mall/app`，数据在 `MALL_DIR/data`（uploads / runtime / backup），配置与密钥在 `MALL_DIR/config`。**任何一次程序替换都不触碰数据。**

## 3. 快速开始（干净机器）

```bash
# 1. 上传源码（排除构建产物）
tar czf mall-src.tar.gz --exclude='node_modules' --exclude='.next' \
    --exclude='.turbo' --exclude='dist' --exclude='.git' .
scp -P 2222 mall-src.tar.gz user@host:/data/home/

# 2. 解压并安装
ssh -p 2222 user@host 'mkdir -p /data/home/mall && tar xzf /data/home/mall-src.tar.gz -C /data/home/mall \
  && cd /data/home/mall && MALL_DIR=/data/home/mall-data bash deploy/install.sh'

# 3. 打开
#    店面  http://<host>/
#    后台  http://<host>/admin/
```

**安装 10 步**：环境探测 → 检查 Docker → 准备目录 → 生成密钥 → 自动调参 → 拉起依赖 → 执行迁移 → 首次种子 → 拉起应用 → 健康检查。

- **必填配置恒为 0**：所有参数有默认值（`--domain` / `--admin-email` / `--locale` / `--offline` / `--no-tuning`）。
- **默认管理员**：`admin` / `123456`（`--admin-email` / `--admin-password` 可自定义）。
  - 未指定 `--admin-password` 时使用默认密码 `123456`，安装日志会直接打印「管理员标识 + 初始密码」，开箱即用。
  - 登录标识可以是管理员名或邮箱（登录校验已放宽）；**顾客注册仍严格要求合法邮箱**。
  - 是否使用强密码由部署方自行决定；系统**不强制改密**，也不做首次登录拦截。
  - 种子幂等：账号已存在则**不覆盖**已有密码（改了密码后重跑安装不会被重置）。
- **密钥自动生成**：`POSTGRES_PASSWORD` / `JWT_SECRET` / `ENCRYPTION_KEY` 写入 `MALL_DIR/config/.env`（0600），compose 通过 `--env-file` 读取。
- **自动调参**：按内存分 S/M/L/XL 四档生成 PG（`shared_buffers` / `work_mem` / `max_connections`）与 Redis（`maxmemory`）参数，小机器保守、大机器放开。

```
运费方案 → 支付商 → 建车 → 加购 → 选运费 → 结账 → 建支付会话 → 授权 → 扣款
→ 查订单（paid/captured）→ 查库存 → 后台登录 → 建发货单 → 发货 → 查订单终态
```

最近一次真机执行结果：订单 `ord_06GW05EF1AWAWJ6C5F5PXQCHJ4` 终态 `paid` / `captured` / `20600`；发货单 `status=fulfilled` 且自动关联预留；库存 `stocked=94, reserved=2, available=92`（`reserved=2` 是修复前那笔未付款订单的预留，仍正确保留）。

**促销三件套验收脚本**（`deploy/scripts/e2e-promotion.sh`，真机可直接跑）：

```bash
bash deploy/scripts/e2e-promotion.sh
# 自定义：BASE=... ADMIN=... ADMIN_PW=... VAR_ID=... bash deploy/scripts/e2e-promotion.sh
```

```
后台建订单促销(满减)并启用 → 建券 → 店面加购 → 选运费 → 自动命中订单促销
→ 输券 → 输礼品卡 → 合计恒等式 → 下单 → 后台订单详情核对折扣留痕
→ 券已核销(used=1) / 卡已扣减 / 流水含 used_in_order
```

断言口径（不写死总额，避免机器上其它促销导致假失败）：

- **增量断言**：`d1-d0` 必须等于券面额，`d2-d1` 必须等于卡实际抵扣额（`min(卡余额, 剩余应付)`）
- **明细断言**：购物车 `discounts` 逐项含本次促销 id / 券码 / 卡码；后台订单 `discounts` 留痕合计 = 订单折扣
- **恒等式**：`total = subtotal + shipping - discount` 且 `total >= 0`
- **清理**：脚本退出时（含中途失败）自动停用本次建的促销与券，记录保留可审计，不会继续命中真实订单

> 依赖 `curl` + `jq`；缺 `jq` 时脚本第一步就会失败并给出安装命令（`apt-get install -y curl jq`）。
> 本脚本会真实下单并消耗一张礼品卡，建议在验收环境执行。

**多仓端到端验收脚本**（`deploy/scripts/e2e-inventory.sh`，真机可直接跑）：

```bash
bash deploy/scripts/e2e-inventory.sh
# 自定义：BASE=... ADMIN=... ADMIN_PW=... PRODUCT_HANDLE=... CONCURRENCY=... bash deploy/scripts/e2e-inventory.sh
```

```
建第二仓 → 拆库存到两仓（主仓只留 1 件）→ 跨仓下单（一单两仓预留）
→ 不指定仓发货被拒 → 按仓分别建发货单 + 运单 → 两仓各自出库
→ 调拨正常搬迁 / 可用量不足被拒 → 并发 10 单各要 3 件（库存 10）只成功 3 单
```

断言口径：

- **跨仓**：预留条数 2、涉及仓数 2；每仓发货单 1 张，运单齐全；两仓在库各 -1、预留各 -1
- **调拨**：可用量不足必须被拒（`stocked - reserved >= qty`），且两边库存不动
- **并发**：库存 10、10 单各要 3 件 → 成功 3 单，`reserved` 恰好 +9，`available = 1`（不超卖）
- **可重复执行**：所有断言用「库存差值」而非绝对值；主仓可用不足 2 件时自动补到 2 件，重复跑不会假失败
- **限流**：下单接口默认 10 次/分钟，并发批次前会等一个窗口（`RATE_WAIT`，默认 61 秒；改过 `RATE_LIMIT_CHECKOUT_MAX` 时相应调整）
- **清理**：退出时取消未完成调拨、把测试仓库存调回主仓、优先级置 0；仓库无删除接口故保留

> 依赖 `curl` + `jq`；会真实下单并在验收环境产生 1 笔跨仓订单 + 3 笔并发订单（均未付款）。

### 5.1 部署 / 编排级（16）

| # | 问题 | 症状 | 修法 |

| 1 | PostgreSQL 18 改了数据目录布局 | 容器启动即退出：`there appears to be PostgreSQL data in /var/lib/postgresql/data` | 挂载改为 `/var/lib/postgresql` |

| 9 | 种子命令路径错误 | `Cannot find module '/repo/dist/seed.js'` | `apps/api/dist/seed.js` |
| 10 | 缺 `public/` 目录 | 镜像 `COPY public` 失败 | 补 `apps/storefront/public/robots.txt` |
| 11 | 健康检查硬编码容器名前缀 | 永远报「容器不存在」（实际是 `deploy-postgres-1`） | 改用 `docker compose ps`，不依赖项目名 |

| 28 | nginx 静态 upstream 固化容器 IP | api 容器重建换 IP 后，nginx 仍指向旧 IP → **全站 502**，且 nginx 自身毫无察觉 | 改「`set` 变量 + Docker 内嵌 DNS `resolver 127.0.0.11`」，按 TTL 重新解析；`/admin/` 前缀用 `rewrite` 剥离。实测：api 换到 172.18.0.10 且旧 IP 被占，nginx **未 reload** 仍返回 200 |

| 31 | compose 同一份代码 build 成三个独立镜像 | 只 build 了 api/worker，**migrator 落后 44 分钟** → 新迁移文件根本没被加载，迁移日志说「共 19 个文件，本次新应用 0 个」，`audit_log` 表**根本不存在**（审计功能等于没有），且全程无任何机制提示漂移 | api/worker/migrator 统一 `image: ${IMAGE_NAME:-mall-app:local}`，只保留 api 的 `build:` 段；`install.sh` 在迁移前显式构建。物理上不可能漂移，顺带省 2/3 构建时间 |
| 32 | 备份与恢复是「假闭环」 | ①`backup.sh` 硬编码 `mall-postgres-1`/`mall_default`（真机是 `deploy-*`）→ 数据库备份**完全失败**，产出 0 字节 dump，但 MANIFEST 用 `-f` 判存在 → 谎报 `db: ok`；②`restore.sh` 的 SHA256 校验对空文件同样"通过"，把 0 字节判成「纯SQL格式」，下一步就是 `DROP SCHEMA public CASCADE` → **清空 80 张表的库** | ①一律用 compose 解析（禁硬编码容器名/网络名）；②状态判定改为**验内容不验存在**（`-s` + 头部 `PGDMP` + 最小尺寸阈值），MANIFEST 区分 `failed`/`skipped`，失败不留空产物且退出码非 0；③`restore.sh` 改为格式白名单判定，空文件/损坏文件一律拒绝且**一行数据库命令都不执行**；④`doctor.sh` 新增独立的 `backup.db.valid` 检查项（不能只靠 SHA256） |
| 33 | nginx DNS 缓存窗口 | 容器重建换 IP 后，nginx 在 DNS TTL 到期前仍用旧 IP → 访问该服务短暂 502（实测 admin 容器 Recreate 后首访 502，数秒后恢复 200） | `resolver ... valid=10s` 收窄为 `valid=2s`（Docker 内嵌 DNS 是本机回环查询，缩短 TTL 几乎零成本）；同时保留变量 proxy_pass 的动态解析能力 —— **这是 #28 修复带来的残留窗口，不是回归**。真机对照实验：`up -d --force-recreate admin` 后立即连打 5 次 `/admin/` → `502 200 200 200 200`（原先 10s TTL 下会持续数秒 502）。注意 `valid` 只能收窄窗口上界、**无法消除窗口本身**（容器换 IP 瞬间 nginx 仍可能握着旧 IP）；改成 `valid=0` 反而会在容器重建期间变成「DNS 查不到就报错」，更糟 |

## 6. 数据源模式切换

店面与后台都支持 **mock / live 双模式**，**同一份代码**，切换只改一个环境变量后重新构建：

| 应用 | 开关 | 生效方式 | 默认 |
|---|---|---|---|
| 店面 | `NEXT_PUBLIC_API_MODE` | `docker build` 的 ARG（构建期内联） | `mock` |
| 后台 | `VITE_API_MODE` | `docker build` 的 ARG（构建期内联） | `mock` |

- **mock**：本地数据 / localStorage 种子，**零后端依赖**，适合演示与前端开发。
- **live**：打真实 API，适合真机联调与生产。

```bash
# compose 环境变量里开启
NEXT_PUBLIC_API_MODE=live
ADMIN_API_MODE=live
cd deploy && docker compose --env-file /data/home/mall-data/config/.env build storefront admin && docker compose --env-file /data/home/mall-data/config/.env up -d storefront admin
```

> [注意] 这两个变量**必须在 build 时**设置（见 #27）。运行时 `docker compose up` 改环境变量对已构建的 bundle 无效。

## 7. 运维手册

### 7.1 健康检查

```bash
bash deploy/healthcheck.sh          # 五项：db / redis / queue / migrations / disk
curl -s http://<host>/api/v1/health
# {"code":0,"data":{"status":"ok","db":"ok","redis":"ok","queue":"ok","migrations":"theme/0001_init.sql"}}
```

### 7.2 备份（升级前必做）

```bash
bash deploy/scripts/backup.sh       # pg_dump + uploads 打包 + 配置快照 → MALL_DIR/data/backup/<时间戳>/
```

产物含 `MANIFEST`（逐项 ok / skipped），配置快照**排除 secrets.json**（不泄漏密钥）。

### 7.3 数据目录

```
MALL_DIR/
├── app/            # 程序（可整体替换）
├── config/         # .env / secrets.json / pg.conf / redis.conf / tuning.env
└── data/
    ├── uploads/    # 用户上传
    ├── runtime/    # 运行时临时
    ├── backup/     # 备份
    ├── pgdata/     # PG 数据卷
    └── redis/      # Redis 数据卷
```

### 7.4 恢复与升级

**升级（换代码）**：

```bash
cd $MALL_DIR/app
bash deploy/scripts/backup.sh                                    # 1) 先备份
# 2) 替换 app/ 目录（程序），数据与配置不动
docker compose --env-file $MALL_DIR/config/.env build api        # 3) 必须先构建镜像
docker compose --env-file $MALL_DIR/config/.env run --rm migrator # 4) 再跑迁移
docker compose --env-file $MALL_DIR/config/.env up -d api worker storefront admin nginx
bash deploy/healthcheck.sh                                        # 5) 健康检查
```

> **第 3 步不能省。** api / worker / migrator 现在共用同一个镜像标签（默认 `mall-app:local`），
> 三个服务里只有 api 带 `build:` 段。不先构建，migrator 就会用**旧镜像**跑迁移 ——
> 新迁移文件根本没被加载，新表不会建出来，而迁移日志还显示「成功」（本项目真机踩过）。
> 核对三处是否同一份镜像：
> ```bash
> docker inspect --format '{{.Image}}' \
>   $(docker compose --env-file $MALL_DIR/config/.env ps -q api) \
>   $(docker compose --env-file $MALL_DIR/config/.env ps -q worker)
> ```
> 两者应输出完全相同的 image ID。

- 回滚：备份里的 `mall.dump` 灌回（`bash deploy/scripts/restore.sh --backup <标签>`）+ 换回旧 `app/` 后**同样要先 `build api`** 再拉起。
- 迁移**只增不删**：破坏性变更由 CI 的 AST lint 拦截（`scripts/lint-migrations.ts`）。

### 7.4b 管理员口令：三条路径与各自的代价

| 路径 | 命令 | 强度规则 | admin_user.id | 用途 |
|---|---|---|---|---|
| **主路径** | 后台改密页 / `POST /api/v1/admin/auth/change-password` | 强制（8位+字母+数字） | **不变** | 日常改密 |
| **应急轮转** | `bash deploy/scripts/set-admin-password.sh --password '<新口令>'` | 强制（同上） | 变化 | 忘记口令 / 账号被锁 |
| **恢复出厂默认** | `bash deploy/scripts/set-admin-password.sh --restore-default --yes` | **绕过**（降级操作） | 变化 | 把口令恢复成出厂默认值 |

> **为什么必须有第三条**：出厂默认口令 `123456` 本身就不满足强度规则（6 位、纯数字）。
> 如果所有路径都强制强度规则，用户一旦改密就再也回不到默认口令 —— 这是规则死锁。
> 所以「用户自选的新口令」受强度规则约束，而「恢复出厂默认值」走产品 seed 自己的
> `DEFAULT_ADMIN_PASSWORD`（脚本刻意**不传** `ADMIN_PASSWORD`，出厂默认值只有一个权威来源）。
>
> ⚠️ `--restore-default` 是**降级操作**：恢复后任何人拿到后台地址都能登录，
> 恢复完请立即用后台改密页改成强口令。脚本会强制要求 `--yes` 并打印醒目警告。
>
> ⚠️ 应急脚本会**软删旧 identity + admin_user** 再由 seed 重建 → `admin_user.id` 变化，
> 角色绑定与审计里的 `actor_id` 会跟着漂。能用改密端点就别用应急脚本。


### 7.5 nginx 反代与容器 IP（真机问题 #28 的运维要点）

`nginx.conf` 以 **bind mount** 挂载进容器，因此：

- **改了配置必须显式 reload**（容器不会自动重载）：
  ```bash
  docker compose exec -T nginx nginx -s reload   # 先 nginx -t 验证语法
  ```
  `install.sh` 步骤 9 已内置这一步，重跑安装即可生效。
- **上游用变量 + 内嵌 DNS 动态解析**（`resolver 127.0.0.11`），容器重建换 IP 后 nginx 会自动跟随，**不需要 reload**。
  旧写法（静态 `proxy_pass http://api:3000`）会在 api 重建换 IP 后全站 502，且 nginx 毫无察觉——这是本项目第 28 个真机问题。
- 排查 502 的顺序：`docker compose ps`（api 是否 healthy）→ `docker exec nginx getent hosts api`（DNS 解析是否正确）→ api 容器内 `wget -qO- http://127.0.0.1:3000/api/v1/health`（服务自身是否正常）。
- **DNS 缓存窗口已收窄到 2 秒**（`resolver 127.0.0.11 valid=2s`）：容器重建换 IP 后，旧 IP 最多再被缓存 2 秒。Docker 内嵌 DNS 是本机回环查询，调小 `valid` 不带来网络开销。原先的 10 秒会在容器重建后留一个 10 秒的 502 窗口 —— 对个人商城可接受，但收窄到 2 秒几乎零成本。
