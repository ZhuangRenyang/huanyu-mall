# ADR-023 退款管理：单据与资金分开，同意才真打款

- 日期：2026-11-12
- 状态：Accepted
- 范围：order 模块、payment 接口、refund-order workflow、admin 退款页、店面申请入口
- 关联：ADR-021（布局照淘宝）、ADR-014（简单优先）

## 背景

按「布局照淘宝」审计时排到退款管理，结果先挖出一个**资金 bug**：

> 后台订单详情的「退款」按钮，只调 `order.markRefundSettled` 把订单状态改成 refunded，
> **从头到尾没有调用 `payment.refundPayment`**。

也就是说：账上显示已退款，钱还在商家账上。这属于最危险的一类问题 —— 界面看起来做完了，
错误只在顾客来问「钱怎么没到」时才暴露，而且没有任何记录可查。

同时缺两块：
- 没有独立的「退款管理」入口（淘宝在「交易 → 退款管理」），只能在订单详情里一条条翻；
- 顾客端**没有任何申请退款的入口** —— 想退款只能找客服。

## 决策

### 1. 单据与资金分成两张表

| 表 | 语义 | 谁写 |
|---|---|---|
| `refund_request`（order 模块） | 售后**单据**：谁、因为什么、退多少、商家怎么处理 | 顾客申请 / 商家主动 |
| `payment.refund` | 资金**流水**：真正打给支付通道的那一笔 | payment 模块 |

不合并的理由：未支付就取消的订单没有资金流水，但可能需要一张申请单留痕；
商家主动发起的大额退款也可能直接走资金流水而不经过申请。两种语义混表必然互相污染。

`refund_request.refund_id` 指向资金流水，同意并执行成功后写入 —— **没有 refund_id 的「已同意」就是没退款**，一眼可查。

### 2. 退款必须走 workflow，且先打款后改状态

`refundOrderWorkflow`：
1. `payment.refundPayment`（compensationClass = I，不可逆）
2. `order.markRefundSettled`（R）

顺序不能反：先改状态，一旦打款失败，就成了「显示已退款、实际没退」，
比不退款更糟 —— 顾客不会再来问，商家也发现不了。

幂等键绑申请单（`refund-approve:${refundRequestId}`）：重复点击不会退两次。

### 3. 状态机单向，四态

```
pending ──同意──> approved（带 refund_id）
   ├──拒绝──> rejected（review_note 必填）
   └──顾客撤销──> canceled
```

- 同一订单同时只允许一条 `pending`（DB 部分唯一索引 + 服务层预检）；
- 已处理的单据不能再处理：**校验放在跑 workflow 之前**。
  反过来写就是「对已拒绝的单子点同意 → 钱先退出去、再报已处理」，正是重复退款的来源。

### 4. 顾客只能申请全额，金额由服务端取

`POST /store/orders/:id/refund-requests` 只收 `reason`。
金额取 `order.total_minor`，客户端不能传（铁律 13）；一期也不支持部分退款。

### 5. 入口按域归位

- 后台：`订单 → 退款管理`（独立页，带状态页签：待处理 / 已同意 / 已拒绝 / 全部）。
  单独成页而不是塞进订单详情 —— 退款有自己的状态与时效，混在订单里就没法「筛出全部待处理」。
- 店面：订单详情底部「申请退款」，已付款订单才出现；提交后显示「商家处理中」，
  已有申请不再显示按钮，避免重复提交。

## 后果

- 订单详情的「退款」按钮现在是**真退款**：建单（source=merchant）→ 跑 workflow → 打款 → 改状态。
- 新增迁移 1 个（`refund_request`）；新增 workflow 1 个；新增接口 5 个
  （list / approve / reject / 顾客申请 / 顾客查进度）。
- `payment` 模块新增 `findPaymentByOrderId`：退款要知道退哪一笔，不该让调用方拼两步查询。

## 验证

- api 129 条（新增 7 条退款：申请落待处理且金额取订单、列表按状态筛、同意后带资金流水号、
  空理由 400、拒绝留理由、已处理再同意 409、不存在 404）。
- 全仓 42 个测试任务、48 个类型任务、25 个构建任务、35 个迁移校验全绿。
