# ADR-023 退款管理：单据与资金分开，人工审核通过才打款

- 日期：2026-11-12
- 状态：Accepted
- 范围：order 模块、payment 接口、refund-order workflow、admin 退款页、店面申请入口
- 关联：ADR-021（布局照淘宝）、ADR-014（简单优先）

## 背景

按「布局照淘宝」审计时排到退款管理，结果先挖出一个**资金 bug**：

> 后台订单详情的「退款」按钮，只调 `order.markRefundSettled` 把订单状态改成 refunded，
> **从头到尾没有调用 `payment.refundPayment`**。

也就是说：账上显示已退款，钱还在商家账上。这属于最危险的一类问题 —— 界面看起来做完了，
错误只在顾客来问「钱怎么没到」时才暴露，而且没有任何记录可查。

同时缺两块：
- 没有独立的「退款管理」入口（淘宝在「交易 → 退款管理」），只能在订单详情里一条条翻；
- 顾客端**没有任何申请退款的入口** —— 想退款只能找客服。

## 决策

### 1. 单据与资金分成两张表

| 表 | 语义 | 谁写 |
|---|---|---|
| `refund_request`（order 模块） | 售后**单据**：谁、因为什么、退多少、商家怎么处理 | 顾客申请 / 商家主动 |
| `payment.refund` | 资金**流水**：真正打给支付通道的那一笔 | payment 模块 |

不合并的理由：未支付就取消的订单没有资金流水，但可能需要一张申请单留痕；
商家主动发起的大额退款也可能直接走资金流水而不经过申请。两种语义混表必然互相污染。

`refund_request.refund_id` 指向资金流水，同意并执行成功后写入 —— **没有 refund_id 的「已同意」就是没退款**，一眼可查。

### 2. 退款必须走 workflow，且先打款后改状态

`refundOrderWorkflow`：
1. `payment.refundPayment`（compensationClass = I，不可逆）
2. `order.markRefundSettled`（R）

顺序不能反：先改状态，一旦打款失败，就成了「显示已退款、实际没退」，
比不退款更糟 —— 顾客不会再来问，商家也发现不了。

幂等键绑申请单（`refund-approve:${refundRequestId}`）：重复点击不会退两次。

### 3. 状态机单向，四态

```
pending ──同意──> approved（带 refund_id）
   ├──拒绝──> rejected（review_note 必填）
   └──顾客撤销──> canceled
```

- 同一订单同时只允许一条 `pending`（DB 部分唯一索引 + 服务层预检）；
- 已处理的单据不能再处理：**校验放在跑 workflow 之前**。
  反过来写就是「对已拒绝的单子点同意 → 钱先退出去、再报已处理」，正是重复退款的来源。

### 4. 顾客只能申请全额，金额由服务端取

`POST /store/orders/:id/refund-requests` 只收 `reason`。
金额取 `order.total_minor`，客户端不能传（铁律 13）；一期也不支持部分退款。

### 5. 入口按域归位

- 后台：`订单 → 退款管理`（独立页，带状态页签：待处理 / 已同意 / 已拒绝 / 全部）。
  单独成页而不是塞进订单详情 —— 退款有自己的状态与时效，混在订单里就没法「筛出全部待处理」。
- 店面：订单详情底部「申请退款」，已付款订单才出现；提交后显示「商家处理中」，
  已有申请不再显示按钮，避免重复提交。

### 6. 审核闸门：申请即冻结，发货端必须拦

只把单据放进列表、订单照常能发货，等于审核没生效 —— 货发出去、钱也退了，是最典型的资损。
所以：

- 新增订单状态 `refund_pending`（淘宝的「退款中」）。**申请退款即转此状态**，
  不再等商家点同意才冻结。
- `refund_request.order_status_before` 记下申请前的状态：拒绝/撤销时**精确恢复**
  （已发货的回「已发货」，未发货的回「待发货」），不能一律回 `paid`。
- 发货两个入口都拦：`POST /admin/orders/:id/fulfillments`（建发货单）与
  `POST /admin/fulfillments/:id/shipments`（填运单号，才是真正发出）。
  只拦前者不够 —— 发货单可能在建单时就已存在。
- `refund_pending` 不能取消订单（状态机不给 `canceled` 出边），两条路会打架。
- **订单详情的「退款」按钮降级为「发起退款申请」**：只建单，不打款。
  在此之前它是「建单 + 立刻执行 workflow」，等于给审核开了一条旁路。
- 商家发起时金额同样由服务端取订单实付，`CreateRefundRequest` 里不再有 `amount_minor`。

### 7. 明确不做自动退款

用户 2026-11-12 定下的边界：**不做自动退款**。

意思是系统里不存在任何「无人值守就会打款」的路径。具体到实现：

| 不做 | 原因 |
|---|---|
| 超时未处理自动同意 | 淘宝有平台兜底，自建商城没有；自动打款出错无人拦截 |
| 定时任务批量退款 | 同上，而且没有对账机制兜底 |
| 取消订单联动退款 | 已付款订单不能直接取消（状态机不给出边），必须先走退款审核；未付款取消只释放库存 |
| 售后系统自动补偿打款 | workflow 的步骤级重试属于单次人工请求内部（有幂等键），不扩成后台退款任务 |
| 任何订阅者触发退款 | `shipment.created` / `payment.captured` 等订阅者都不得调 `payment.refundPayment` |

**唯一打款入口**：`POST /admin/refund-requests/:id/approve`，必须由商家在「退款管理」点「同意退款」。
新增退款触发点需要先推翻这条规则，不是加个开关就行。

## 后果

- 订单详情的「退款」按钮改为**发起申请**：建单（source=merchant）→ 进待处理 → 由
  「退款管理」审核通过才打款。打款入口全仓只剩 `POST /admin/refund-requests/:id/approve` 一个。
- 新增迁移 2 个（`refund_request`、`refund_pending`）；新增 workflow 1 个；新增接口 5 个
  （list / approve / reject / 顾客申请 / 顾客查进度）。
- `payment` 模块新增 `findPaymentByOrderId`：退款要知道退哪一笔，不该让调用方拼两步查询。
- 后台订单列表新增「退款中」筛选；「待发货」筛选**排除**退款中的订单
  （商家照着待发货列表发货，混进去就会出错）。

## 验证

- api **135 条**：申请落待处理且金额取订单、列表按状态筛、同意后带资金流水号、
  空理由 400、拒绝留理由、已处理再同意 409、不存在 404；
  以及审核闸门 6 条 —— 订单详情只建单不打款（refund_id 为 null）、
  退款中建发货单 409、退款中填运单号 409、同意后订单 refunded、
  列表带状态计数、客户端传的金额被忽略（仍按订单实付退）。
- order 模块 **15 条**（新增 6 条）：申请即转退款中、重复申请被拒、退款中不能取消、
  拒绝回到申请前状态（已发货仍回已发货）、撤销恢复、同意后已退款。
- 全仓 42 个测试任务、48 个类型任务、25 个构建任务、36 个迁移校验全绿。
