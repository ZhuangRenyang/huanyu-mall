# ADR-003: links 关联层 = 中间表 + 声明式 registry + repository 组合

## Status: Accepted (2026-11-08)

## Background

铁律 2：模块间禁止数据库外键，跨模块关系走 links 关联层，替换单个模块影响面只限本模块 + 调用它的 workflow。候选：纯中间表 + 手写 repository、独立 link service（每个关系一个服务类）、ORM relation 代理（Drizzle 的 `relations()` 定义跨表关系）、对齐 Medusa 的声明式 `defineLink` + 中间表生成。

Medusa 的真实形态（已核实）：`packages/modules/link-modules/src/definitions/product-sales-channel.ts` 用 `ModuleJoinerConfig` 声明 `databaseConfig.tableName`、`primaryKeys`、`relationships`、`extends`（把关系反向挂到实体），运行时生成独立中间表并支持 `Link.create/dismiss/delete/restore`（见官方文档 module-links/link）。

## Decision

采用「声明式 registry + 中间表 + repository 组合 + query-composer」，对齐 Medusa 结构但自研：

- **声明式**：`defineLink({ table, left: { module, entity, key }, right, cardinality, onDelete, columns })`，启动时 `link-registry` 校验（表名唯一、字段存在、无循环级联）。
- **中间表**：关系本身生成独立表（多对多/装配型）；归属型（cart→channel 这类 1:1 从属）只存 id 列、不建外键、不生成中间表，只在 `linkable.ts` 声明白名单供 join。
- **repository 组合**：`LinkRepository` 提供 `create/dismiss/delete/restore/listByLeft/listByRight/batchGet`，全部幂等。
- **query-composer**：唯一允许跨模块读的地方，把「主查询 + 若干 link」编译成一条带 LEFT JOIN 的 SQL，禁止 N+1。
- **删除语义三值**：`restrict`（默认）/ `dismiss`（调用方 workflow 显式解除）/ `cascade`（仅限 1:1 且生命周期完全从属，须登记理由）。

完整关联表清单（13 张）与字段/索引/删除语义见 ARCHITECTURE.md §4.3。

## Consequences

正面：
- 满足铁律 2：替换一个模块，影响的只有它自己的表 + 它作为一端的 link 声明 + 调用它的 workflow。
- 关系有独立生命周期（`is_visible`、`sort_order` 等关系属性不污染业务表）。
- `query-composer` 杜绝了"为凑一个字段在循环里 resolve 别的模块"的 N+1 反模式。
- 未来拆库时，query-composer 是唯一的替换点（改成本地 join → 远程聚合），业务代码不动。

负面：
- 比直接开外键多一层间接，join 查询由 composer 生成，团队需要理解"id 列无外键 + link 声明"的心智模型（有学习成本）。
- 一期不支持跨库 join（单库内）；拆库时 composer 需重写。
- 关联表软删 + 唯一索引需要 `WHERE deleted_at IS NULL` 部分索引（§16 坑 4），否则 dismiss 后无法重建同一条关联。

## Alternatives

1. **ORM relation 代理（Drizzle relations）**：定义快、查询直观，但 relation 只存在于类型层，不解决"模块边界"——A 模块 import B 模块的 schema 才能定义 relation，破坏了铁律 2 的隔离。否决。
2. **独立 link service（每个关系一个类）**：语义最直白，但 13 张关联表 = 13 个服务类，样板代码爆炸，且无法统一做"一次 join 多关系"的 composer。否决。
3. **纯手写中间表 + repository，无声明式**：最简单但失去"启动时校验表名/字段/循环级联"的防线，容易漏声明。否决。
