# ADR-027 找回密码：验证码重设，兼作「首次设密码」

- 日期：2026-11-12
- 状态：Accepted
- 范围：auth 模块（重置流程、会话撤销）、API 店面路由、storefront 认证表单、SDK
- 关联：ADR-025（注册方式与验证码双通道）、ADR-007（refresh 轮换与黑名单）

## 背景

注册体系做完后，顾客侧还剩一个硬缺口：**忘记密码没有任何入口**。

- 邮箱注册的顾客忘了密码 → 只能找客服；
- 手机号注册的顾客**从来没有密码**（注册即登录）→ 想用「手机号 + 密码」登录也没有地方设置。

成熟系统两条路线：

| 做法 | 参照 | 问题 |
|---|---|---|
| 手机号 + 验证码直接重设 | 淘宝「忘记密码」 | 需要可用的手机号（我们注册时强制验证过，成立） |
| 邮箱发一次性重置链接 | Shopify | 手机号注册的顾客没有邮箱，这条路对他们是死路 |

## 决策

### 1. 走验证码重设，不做重置链接

理由不是「简单」，而是**覆盖所有人**：ADR-025 之后每个顾客身份都至少有一个验证过的
手机号（邮箱注册强制填手机号并验证），也有可能有邮箱。验证码重设对两种账号都成立，
邮件链接只对邮箱账号成立。

验证码基建已经现成：`verification_code` 表、`purpose = "reset"`、
5 分钟有效 / 60 秒冷却 / 每日 10 条 / 错 5 次作废，全部复用。

### 2. 通道跟着账号类型走，不让顾客再选一次

输的是邮箱就发邮件、输的是手机号就发短信。注册时让顾客选通道是必要的（他可能只收得到一种），
找回密码时不必：**他填的是哪个账号，码就该发到哪个地址**。

### 3. 账号不存在就明确说

不学 Shopify 的「如果账号存在，我们已发送」：

- 顾客看到「已发送」却永远收不到码，只会转头找客服；
- 注册接口本来就会返回「邮箱/手机号已注册」，登录接口也能间接判断，藏这一处没有意义；
- 淘宝同样直接提示「该手机号未注册」。

代价是「账号是否存在」可被查询 —— 用严格限流（见 6）压低批量探测的价值。

### 4. 重置 = 覆盖密码，没有密码就插入

手机号注册的顾客没有 `auth_credential` 行。这条路径对他们是「设置密码」，
所以 credential 不存在时是 `insertCredential` 而不是报错。
淘宝也是同一个入口：短信验证通过后设置登录密码。

### 5. 成功后撤销全部会话，且不签发 token

- 密码变了旧登录必须立刻失效，否则「密码被改」对已登录的设备毫无影响 —— 那等于没改；
- **不自动登录**：让顾客用新密码登一次，既验证密码记住了，也不给「拿到验证码就能接管账号」
  多留一步（验证码是弱凭据，密码才是账号主体）。

撤销逻辑抽到 `services/session-revoke.ts`，与管理员改密共用：
两处逻辑一旦分叉，总有一天只有一处撤销干净。

### 6. 两个端点并入严格限流桶

`/store/auth/password/forgot`、`/store/auth/password/reset` 与登录共用 `auth` 档计数。
发码是「会花钱、会给陌生人发消息」的动作；重置是凭据操作 —— 都不该有独立的宽松配额。

## 接口

```
POST /store/auth/password/forgot   { identifier }                    → { sent, channel, dev_code? }
POST /store/auth/password/reset    { identifier, code, new_password } → 204
```

`identifier` 同时接受邮箱与手机号：含 `@` 按邮箱走，否则按手机号校验格式。

## 后果

- 顾客侧闭环补齐：注册、登录、找回密码、我的订单、地址簿都能自助完成。
- 手机号注册的顾客获得了「用密码登录」的能力，但**不影响**验证码登录（两条路并存）。
- 重置成功会踢掉所有设备：顾客在另一台设备上会被登出，这是安全上的正确行为，
  界面上给一句「密码已重设，请用新密码登录」。

## 不做

- **不做重置链接 / 重置 token 表**：验证码已经覆盖同样场景，多一套 token 就多一处过期与重放漏洞。
- **不做安全问题**：答案往往比密码还好猜，成熟系统早已淘汰。
- **不做「最近登录设备」列表与逐设备下线**：需要设备指纹，收益低于复杂度；全量撤销足够。
- **不做重置次数统计与风控**：单店规模用不上，等有真实滥用再加。
