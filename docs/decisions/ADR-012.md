# ADR-012：二期 Promotion 三件套 + Gift Card 建模

- 状态：已采纳（2026-11-10）
- 决策者：项目负责人（用户）点单进入二期第一项
- 关联：蓝图铁律 1（模块化）、铁律 4（扩展机制）、铁律 6（事件）、简报第五期（参考 Saleor 促销建模）、ADR 系列（模块图分层）
- 参考来源（简报授权可复用，已登记）：Medusa `packages/modules/promotion`（MIT）、Saleor `saleor/discount`（BSD-3）

## 背景

一期已交付 13 个模块，交易闭环打通，且 `discount_minor` 字段已在 cart/order 预留（恒为 0）。二期第一项按简报定义是：

> Promotion（按**目录促销 / 订单促销 / Voucher** 三套分离建模 + **礼品卡独立成账**）

这是后续所有折扣类功能的唯一地基。建模错了，会导致折扣算错、优惠券超用、礼品卡套现——都是资金级事故。

## 决策

### 1. 实体：四张主表 + 规则/流水子表

采用 Saleor 的「三套分离 + 礼品卡」骨架，融合 Medusa 的规则三元组思想。**不引入 Campaign 层**（两家参考仓库都显示单商户场景 Campaign 是纯负担：Medusa 2.12 已把限次下沉到 Promotion，Saleor 用 Promotion 的 `start_date/end_date` 直接承载时间窗口）。

| 表 | 用途 | 关键字段 |
|---|---|---|
| `promotion` | 目录促销 + 订单促销（一个实体装两套，`type` 区分） | `code`(自动促销码)、`type`(`catalogue`\|`order`)、`status`(`draft`\|`active`\|`inactive`)、`is_automatic`、`starts_at`、`ends_at`、`usage_limit`、`used`、`metadata` |
| `promotion_rule` | 一条促销的「条件 + 动作」 | `promotion_id`、`predicate`(JSON，见下)、`reward_type`(`fixed`\|`percentage`)、`reward_value`、`allocation`(`each`\|`across`\|`once`) |
| `voucher` + `voucher_code` | 优惠券（一券多码，每码独立计数） | voucher：`type`(`entire_order`\|`shipping`\|`specific_product`)、`usage_limit`、`starts_at`/`ends_at`、`discount_type`/`discount_value`、`min_spent`；voucher_code：`code`(唯一)、`used`、`is_active` |
| `gift_card` + `gift_card_event` | 礼品卡（独立成账） | gift_card：`code`(唯一)、`currency`、`initial_balance`、`current_balance`、`is_active`、`expires_at`；gift_card_event：`type`、`amount`、`order_id`(可空)、`parameters`(JSON) |

### 2. 条件引擎：类型化 JSON predicate

采用 Saleor 的嵌套 predicate 结构，但用 TS 类型约束（比 Saleor 的字符串 key 更规整）：

```ts
type Predicate =
  | { and: Predicate[] }
  | { or: Predicate[] }
  | { variantIds: string[] }          // 目录促销：指定变体
  | { categoryIds: string[] }         // 目录促销：指定分类
  | { collectionIds: string[] }       // 目录促销：指定集合
  | { subtotalGte: number }           // 订单促销/券：小计门槛（minor unit）
  | { currencyEq: string };           // 币种匹配
```

存 `jsonb`，计算时用 TS 函数求值（不依赖 DB 反查），扩展维度只需加 union 分支。

### 3. 折扣落库：cart 行级 adjustment + order 级 discount

- **目录促销** → 行级折扣，落到 cart 已有的 `cart_line_item_adjustment`（需扩展 `promotion_id`、`code`、`is_tax_inclusive` 字段）。
- **订单促销 / Voucher** → 订单级折扣，落到 `order.discount_minor`（已有字段）。
- **行级分摊决策**：一期**不做**订单级折扣的行级分摊持久化（Saleor 也不做，只在计税时临时摊）。退款/部分退款时按 `discount / subtotal` 比例摊——这是二期税务深化前的简化，已在 OPEN-DECISIONS 登记。

### 4. 模块分层与计算入口

- 新增 `@mall/promotion` 模块，**layer 2**（与 pricing/tax 同层，被 cart 依赖）。
- cart 通过 port（`PromotionLookupPort`）调 promotion 模块算折扣——**不是 cart 直接 import promotion**，遵守铁律 13（模块间走 port）。
- 计算时机：`retrieveCart` 读时动态算（与 B1 修复的 totals 动态计算同一模式），不落库到 cart.totals 外，而是把 adjustment 行和 discount 算出来返回。

### 5. 折扣计算入口

仿 Medusa 的 `computeActions`，promotion 模块暴露：

```ts
computeDiscounts(ctx: {
  currencyCode: string;
  customerId?: string | null;
  items: Array<{ id: string; variantId: string; categoryIds: string[]; quantity: number; unitPriceMinor: bigint }>;
  subtotalMinor: bigint;
  shippingMinor: bigint;
  voucherCodes: string[];
  giftCardCodes: string[];
}): Promise<{
  lineAdjustments: Array<{ itemId: string; amountMinor: bigint; promotionId: string; code: string }>;
  orderDiscountMinor: bigint;
  voucherDiscountMinor: bigint;
  giftCardAppliedMinor: bigint;
}>
```

### 6. Gift Card 独立成账

- `current_balance` 是缓存，`gift_card_event` 是账本流水（event sourcing 式）。
- 余额非负：DB 约束 `current_balance >= 0`。
- 结账时 gift card 抵扣在 payment 之前算，扣到 0 则跳过支付。
- 防套用：`assigned_to`（可空）限制只能指定客户用；币种必须匹配渠道。

## 实施顺序（严格分阶段，每阶段 100% 再进下一阶段）

| 阶段 | 内容 | 产出 |
|---|---|---|
| 1 | promotion 模块骨架 + 迁移（4 主表 + 子表） | 模块、DDL |
| 2 | 目录促销（catalogue）：predicate 求值 + 行级折扣 | cart adjustment 落库 |
| 3 | 订单促销（order）：subtotal_discount | order.discount_minor |
| 4 | Voucher：一券多码 + usage 追踪 + 行锁防并发 | 优惠券 CRUD + 结账抵扣 |
| 5 | Gift Card：余额 + 流水 + 结账抵扣 | 礼品卡闭环 |
| 6 | 店面/后台 UI + 端到端验证 | 双端可用 |

## 资金安全硬约束（用户 2026-11-10 明确要求，最高优先级）

> 「优惠券需要通过后台控制，订单促销和抵扣关于钱的都需要后台可控制，避免出现漏洞造成损失。」

这是贯穿所有阶段的铁律，违反即打回：

1. **一切关于钱的配置只能走后端 + 后台**：折扣值、门槛、限额、启用状态、有效期，全部由 admin API 写入（RBAC 保护），店面只读折扣结果。客户端**永不**能指定折扣金额、折扣率、抵扣额。
2. **金额一律服务端计算**（延续铁律 13）：店面只传 `voucher_code` / `gift_card_code` 这类**凭证**，金额由后端 `computeDiscounts` 算出，杜绝客户端传价。
3. **防超用/防套现**：Voucher 的 `used` 自增、GiftCard 的余额扣减，都必须走数据库**行锁 + 事务**，不能「先查后写」产生竞态。
4. **余额非负**：GiftCard `current_balance >= 0` 用 DB 约束兜底，不能靠应用层判断。
5. **后台留痕**：所有促销/优惠券/礼品卡的创建、修改、启停、手动调账，都写审计日志（复用一期 audit 模块），可追溯「谁在什么时候改了什么」。
6. **停用即时生效**：后台停用某促销/券/卡后，下一次 `computeDiscounts` 立即不命中，不能有缓存窗口。
7. **抵扣金额不超过应付金额**：任何折扣/抵扣累计不得超过订单应付（小计+运费+税），结果为负直接归零，杜绝「倒找钱」。
8. **凭证唯一 + 不可预测**：voucher_code / gift_card code 由后端生成（随机高熵），不接客户端自定义码。

## 已知取舍（登记 OPEN-DECISIONS）

1. 订单级折扣不做行级分摊持久化（退款按比例临时摊）—— 税务深化前简化
2. 目录促销「变体价格实时算」不做 Saleor 的 `variants_dirty` 缓存重算（单商户量小，实时算足够）
3. 不做 `buyget`（买 X 送 Y）与赠品 `gift` 奖励 —— 用户 2026-11-10 确认先不做
4. 不做 Campaign 预算池 / 按客户限额 —— 单商户无此需求

## 违反此决策的风险

- 若把优惠码做成 Promotion 的字段而非 VoucherCode 子表 → 一券多码做不了，且使用计数会串
- 若把订单级折扣逐行摊分持久化 → 退款/部分退款逻辑复杂度飙升，且税务未深化前是过度设计
- 若在 cart 里直接 import promotion 模块（不走 port）→ 违反铁律 13，模块图门禁会拦
- 若折扣金额由客户端传 → 直接资损，铁律 13 明确禁止
- 若 voucher/gift card 计数不做行锁 → 并发下单超用，资损
