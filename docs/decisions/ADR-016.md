# ADR-016 订单邮件通知：事务性 outbox + 后台派发

- 日期：2026-11-11
- 状态：Accepted
- 范围：通知模块、订单事件订阅、后台通知设置与记录

## 背景

一期把「通知」留成了空壳：`order.placed` 的 subscriber 只有一行注释，发货也不发任何通知。
商家发完货只能自己去微信/电话告知顾客运单号。

要做两封交易类邮件：

1. **下单确认**（已付款后发）
2. **发货通知**（每次发货发一封，带承运商与运单号）

技术上有一个必须先解决的问题：**本项目的事件总线是同步分发**。

```ts
// packages/core/src/event/event-bus.ts
await this.writer.append(event);          // 落 outbox
for (const handler of handlers) await handler(event);  // 同步 await
```

如果在 subscriber 里直接连 SMTP，一次握手失败就是 10–60 秒，**下单和支付请求会被一封邮件拖死**。
而且 SMTP 是不可靠外部依赖：超时、限流、被对方拒收都属常态。

## 决策

### 1. 事务性 outbox：事件里只落库，不发信

- subscriber 收到事件后**只做渲染 + 插入 `notification` 行**（`status = 'pending'`），毫秒级完成。
- 独立的 `NotificationDispatcher` 每 5 秒领取一批 pending 行发送，成功/失败回写。

这样请求链路里只有一次 INSERT；SMTP 再慢也只影响邮件本身，不影响成交。

### 2. 领取用一条原子 UPDATE，天然支持多进程

```sql
UPDATE notification SET status = 'sending', attempts = attempts + 1
WHERE id IN (
  SELECT id FROM notification
  WHERE status = 'pending'
    AND (next_attempt_at IS NULL OR next_attempt_at <= now())
  ORDER BY created_at
  LIMIT $1
  FOR UPDATE SKIP LOCKED
)
RETURNING *
```

`SKIP LOCKED` 保证多实例部署时同一行不会被两个进程同时发。不使用 BullMQ/Redis：
单商户量级每 5 秒一次轮询足够，多一个中间件只是多一处会挂的东西（ADR-014 简单优先）。

### 3. 幂等靠唯一索引，不靠「记住发过没有」

`dedupe_key` 唯一索引：

- 下单确认 → `order:<orderId>:confirmation`
- 发货通知 → `fulfillment:<fulfillmentId>:shipment`

事件是 at-least-once，重投时 `INSERT ... ON CONFLICT DO NOTHING` 直接挡住，不会给顾客发两封。
两张发货单天然是两封邮件，因为 key 里带的是 fulfillmentId 而不是 orderId。

### 4. 下单确认以「付款成功」为准

`order.placed` 发生在付款之前。此时发「订单已确认」，顾客会以为已付款；
之后再发一封「已付款」又变成两次打扰。所以：

- `order.placed`：保持不发（留注释说明原因）
- `payment.captured`：发下单确认

未付款的订单不发确认信，与「催付」这件事分开——催付不在本期范围。

### 5. 失败重试有上限，且必须能在后台手动重发

- 失败：`status = failed`、记录 `error`（截断 500 字）、`next_attempt_at = now() + attempts 分钟`
- `attempts >= 3` 不再自动排期
- 后台「通知记录」可看到失败原因并手动重发（重置为 pending 后立即发一次）

自动重试无限循环会把一个写错的 SMTP 配置变成持续刷日志的机器。

### 6. 开关默认关闭，密码加密存储

- `notification_settings.enabled` 默认 `false`：没配 SMTP 就发不出去，默认关是诚实状态。
  与营销功能默认关不同，这是交易类邮件——商家配好 SMTP 后只需打开一次。
- SMTP 密码用 AES-256-GCM 存储，主密钥复用部署时生成的 `ENCRYPTION_KEY`；
  接口只返回 `smtp_password_set`，**密码本身永不出接口**，审计日志也只记录是否配置。

## 后果

**收益**

- 邮件再慢也不影响下单与支付；发信失败可见、可重试、可追溯。
- 事件重放不会重复发信；拆单发货每仓一封，符合顾客预期。
- 商家在后台一页完成「开关 + SMTP + 测试发送 + 记录查看」。

**代价与风险**

- 邮件最多延迟约 5 秒（轮询间隔）。对交易类邮件可接受；不是实时聊天。
- 单进程内定时器派发：进程挂掉时 pending 行会留到下次启动，不会丢，但也不会立刻发。
- `ENCRYPTION_KEY` 轮换会导致旧密码解不开——需重新填一次 SMTP 密码（与支付密钥同一约束）。
- 邮件模板是硬编码的 HTML，不支持商家自定义；多语言也不做（ADR-014）。

## 不做

- 不做营销邮件、群发、订阅/退订列表（ADR-014 永久不做营销玩法）
- 不做短信、站内信、Webhook（没有外部系统要对接）
- 不做附件、图片内嵌、自定义模板编辑器
- 不做「催付邮件」——它与下单确认是两种语义，混在一起会让顾客收到互相矛盾的信
