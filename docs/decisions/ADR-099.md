# ADR-099：限时秒杀——活动库存独立于仓库库存，条件更新防超卖

- 日期：2026-11-14
- 状态：已采纳
- 关联：ADR-012（促销计算）、ADR-064（券范围）、ADR-094（积分抵扣）、ADR-097（统计）

## 背景

D 期营销里，促销只有「折扣」一种形态：满减、券、礼品卡、积分。缺的是**限时限量**：
商家想做「今晚 8 点，100 件 5 折」，现在只能用普通促销近似 —— 但普通促销不限量，
卖多少算多少，也没有「抢完即止」的紧迫感。

淘宝和 CRMEB 都有独立的秒杀：活动有时间窗、有活动商品、有活动库存。

## 决策

### 1. 活动库存是「营销限量」，独立于仓库库存（两道闸）

`flash_sale_item.stock/sold` 记的是**本次活动最多卖多少**，不是仓库有多少。

- 活动库存：管「这次活动放多少」，卖完就恢复原价；
- 仓库库存：管「实际有多少货」，由 inventory 模块在发货链路上扣。

两个都要过。把它们合成一个数就会出现：活动改了库存，仓库跟着变 —— 商家不敢用。

### 2. 秒杀价替换原价，在所有促销之前算

`computeDiscounts` 第一步就查命中的秒杀行，产出 `flashAdjustments`（行级优惠）。
之后的满减门槛、券的适用小计、礼品卡与积分的剩余应付，全部基于**折后金额**。

否则会出现「用秒杀价去凑满减」：原价 100 秒杀 60，满 90 减 10 还能再减 10 —— 商家不会接受。

时间窗与售罄在 SQL 里过滤（`status=active` + `starts_at<=now<ends_at` + `sold<stock`）：
过期的、没上架的、卖完的一律不参与，顾客看到的就是原价。

### 3. 不超卖：条件 UPDATE + DB CHECK + 整单回滚

扣库存只有一条路：

```sql
UPDATE flash_sale_item SET sold = sold + n
WHERE id = ? AND sold + n <= stock
```

返回 0 行 = 售罄。**先查后写必然在并发下超量**，这是唯一有效的手段；
DB 再加 `CHECK (sold <= stock)` 兜底。

`consumeFlashStock` 在 workflow 里是一个独立步骤：售罄抛错 → 整单回滚（订单不成立）。
方法内部已成功的部分扣减要自己回滚 —— engine 的补偿只覆盖**已完成**的步骤，
步骤内部的部分写入不会被回退。

### 4. 先建草稿，显式上架；状态机 draft → active → ended

不做「建完就开卖」：价格填错的秒杀一旦开卖就是资损。草稿阶段可核对，上架后生效。
已结束的活动不能重新上架（卖过的库存与订单已成事实），要再卖就新建活动。

### 5. 原价快照只用于展示与校验，不参与计价

`original_price_minor` 由后台带入（来自商品列表），服务端只校验「秒杀价 < 原价」。

实际计价用的是**购物车里那一行的真实单价**：秒杀价若不低于真实单价，直接不生效
（`if (unitPrice <= flashPrice) continue`）。所以即便原价快照填错，也不会倒贴卖。

### 6. 秒杀挂在 promotion 功能开关下

不新开一个开关：秒杀属促销域，与目录促销同开同关，避免「促销关了秒杀还在跑」的半开状态。

## 遗留

- **取消/退款不退回活动库存**：下单占用的额度在取消后不会还回去。方向是保守的
  （少卖，不会超卖），但会让活动提前「卖完」。补法：加 `flash_sale_redemption`
  （活动商品 + 订单 + 件数）在取消/退款时按订单释放
- **每人限购**：现在不限。需要按顾客统计已购件数，同样依赖兑换明细表
- **秒杀预告与开抢提醒**：现在只展示进行中的活动；预告需要活动列表接口放开 draft/未来场次，
  再接到货提醒那条邮件链路上
- **倒计时**：店面页只有时间文案，没有倒计时组件（纯前端增强）
- **活动商品跳转商品页**：秒杀行只有变体 id，没有商品 slug，现在不可点击
