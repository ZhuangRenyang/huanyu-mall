# ADR-029 可领取的店铺券：商品页领取 → 卡券包 → 结账自动可用

- 日期：2026-11-12
- 状态：Accepted
- 范围：promotion 模块（券公开领取、领取记录、核销联动）、API（`store/vouchers`、`store/customer/vouchers`）、
  admin（券表单「店铺券」开关）、storefront（商品页券条、账户页卡券、结账选券）
- 关联：ADR-012（促销与券码）、ADR-016（通知）、ADR-024（顾客账号）

## 背景

后台早就能建促销、优惠券、礼品卡，但**顾客根本不知道有券**：
店面唯一的入口是结账页一个「输入优惠码」的框。这等于把营销预算埋在了收银台下面。

成熟系统的做法是另一条路：

| | 淘宝 | Shopify | 我们（改造前） |
|---|---|---|---|
| 顾客怎么拿到券 | 商品页「领取」，进卡券包 | 拿 discount code | 必须拿到一串码 |
| 结账怎么用 | 卡券包里自动可选 | 输码 | 输码 |
| 顾客知不知道有券 | 商品页就写着 | 靠商家在站外发码 | 不知道 |

## 决策

### 1. 做「可领取的店铺券」，不做券包/领券中心

先解决「看不到」。`voucher` 上加两个字段（`is_public`、`collect_limit`），
后台勾一下这张券就能在店面公开领取；店面的入口放在**商品详情页**（价格下方），
和淘宝一样 —— 顾客在看商品的时候顺手领，而不是专门去一个「领券中心」页。

### 2. 领取 = 自动发一条专属券码

这是整个方案最关键的一点：**核销链路一行都不用改**。

- 领取时生成一条 `voucher_code`（10 位、去掉易混的 I/O/0/1），
- 同时写一条 `voucher_collection` 记录「谁领了哪张券、换到哪条码」。

于是 `consumeVoucherCodes` / `releaseVoucherCodes` / 溢出保护 / 订单补偿全部照旧生效，
领券只是「把码替顾客记下来」。不做第二套核销逻辑，就不会有两套金额口径。

### 3. 限领与幂等

- `collect_limit` 是每人限领张数（默认 1）。
- 已领满时返回**手里已有的码**（`already_collected: true`），不报错 ——
  顾客连点两下不该看到红字。
- 并发下极小概率多领一张（两个请求同时读到 0 条），影响是商家多给一张券，
  比给「领取」加一把分布式锁划算得多；这一点写在这里，不假装不存在。

### 4. 三个入口，各司其职

| 位置 | 作用 |
|---|---|
| 商品详情页券条 | 让顾客**知道**有券，点一下领取 |
| 账户页「我的卡券」 | 让顾客**查得到**领了什么、什么时候过期 |
| 结账页「我的优惠券」 | 让顾客**用得上**，点选即套用（不必输码） |

未登录点领取 → 跳账户页。不做「先记本地、登录后补领」：那种半接状态最容易出现
「领了却用不了」。

### 5. 过期不落库

`voucher_collection.status` 只有 `unused` / `used`。「已过期」由 `ends_at` 现算。
落一个 `expired` 状态就得跑定时任务去改，改漏了还会出现「页面说可用、后端拒绝」。

### 6. 门槛不满足只提示，不阻止点选

结账页对未达门槛的券显示「未满门槛」，仍可点（后端最终裁决）。
前端不做金额判断的最终裁决 —— 金额一律服务端算，这是铁律。

## 后果

- 商家勾一下「店铺券」，商品页立刻出现券条；不用发码、不用站外投放才能让顾客知道。
- 「我的卡券」与结账选券复用同一条 `voucher_collection` 数据。
- 已有券码链路（手动发码、后台追加码）完全不受影响，两种方式并存。

## 不做

- **不做领券中心 / 券包页**：单店没有那么多的券要逛，商品页 + 账户页足够。
- **不做自动选最优券**：顾客点选比系统猜更可控；自动叠加多个券属于另一个量级的问题。
- **不做券转赠 / 分享领券**：涉及券归属转移与风控，收益不明。
- **不做「领取」的库存耗减**：`usage_limit` 是**核销**上限，领取不占用；
  否则会出现「领了 100 张没人用，活动提前结束」。
