# ADR-096：店面结账「用积分」入口

- 日期：2026-11-14
- 状态：已采纳
- 关联：ADR-093（积分发放）、ADR-094（积分抵扣）、ADR-095（退款退回）

## 背景

积分服务端链路（发放 → 抵扣 → 退款退回）已闭环，但顾客在结账页**没有地方
说「我要用积分」**。没有入口，积分抵扣对顾客等于不存在。

## 决策

### 1. 输入框只传点数，金额永远后端算

结账「用积分」区块：显示当前余额 + 输入想用的点数 + 应用/清除 chip。

前端只调 `setCartPointsToUse(cartId, points)` 传点数，抵扣金额由
`computeDiscounts` 服务端折算封顶（铁律 13）——与券码、礼品卡同一纪律。

### 2. 展示口径以后端为准

- 余额从 `GET /store/points` 拉，未登录/失败显示 0、输入框禁用；
- 已用积分显示为可清除的 chip（「N 积分」），清除即传 0；
- 折扣明细里积分抵扣以 `type="points"` 单独一行（DISCOUNT_LABEL 映射「积分抵扣」）；
- 功能开关 `points` 关闭时不渲染积分区块（与券码/礼品卡一致）。

### 3. 换车下单要重放积分

`prepareCartForOrder` 在换车时只搬行、不搬积分，下单前必须把
`points_to_use` 重新落到最终 cartId——否则展示价与实收价不一致（与券码
ADR-050 的同款教训）。

## 后果

- API：`mapCart` 透出 `points_to_use`
- SDK：`Cart.points_to_use`、`CartDiscount.type` 加 `points`、`setPointsToUse`
- 店面：结账「用积分」输入区块 + 已用 chip + 余额提示；`DISCOUNT_LABEL` 加「积分抵扣」
- 测试：无新增后端逻辑，storefront 46、api 343 保持通过；无迁移

## 遗留

- **积分抵扣的实时预览**：现在输入点数后要「应用」才重算合计；等下单前统一重算
- **余额不足提示**：输入超过余额的点数，服务端会按余额封顶，但前端不预先拦截，
  可后续加「最多可用 N 点」的即时提示
