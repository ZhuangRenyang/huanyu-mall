# ADR-017 后台一键升级：宿主升级代理 + 可配置更新源

- 日期：2026-11-11
- 状态：Accepted（用户选型：装宿主升级代理「真一键」+ 可配置更新源 URL）
- 范围：版本身份、更新源、升级作业队列、宿主代理、后台系统页

## 背景

程序/数据分离的地基一期就打好了（`MALL_DIR/{app,config,data,backup}`、版本化增量迁移、
`backup.sh`/`restore.sh`/`doctor.sh`）。缺的是「谁来执行升级」。

有一个绕不开的事实：**API 跑在 Docker 容器里**，它既替换不了宿主上的源码目录，
也调不了 `docker compose` 重建自己。所以「后台点一下就升级」不可能只在 API 内部实现。

## 决策

### 1. 拆成两半，中间用作业队列连接

```
后台 ──► API ──► system_update_job（Postgres）
                     ▲                │
                     └── 进度/结果 ────┤
                                      ▼
                            宿主升级代理（systemd: mall-updater）
                              备份 → 下载校验 → 替换源码
                              → install.sh → 健康检查 → 失败回滚
```

- **API 只排作业、拉更新源清单、展示进度**。它不执行任何宿主命令。
- **代理在宿主机上**，用 `UPDATER_TOKEN` 调 `/api/v1/system-update/agent/*` 领作业。
  它只需要能跑 bash/curl/jq/sha256sum 和 docker，不需要业务数据库权限。

### 2. 代理装在 `config/` 而不是源码目录

升级第一步就是把源码目录整个 `mv` 走。代理脚本若放在源码里，bash 读到一半就断。
`install.sh` 每次安装都把它复制到 `$MALL_DIR/config/mall-updater.sh`（配置目录，
程序替换永不覆盖），并用 `mv` 原子替换——旧进程继续读旧 inode，不会被截断。

### 3. 失败必须自动回滚

升级流程每一步都可能失败：备份、下载、校验、解压、重建镜像、迁移、健康检查。

- 校验不过 / 解压失败 / 包结构不对 → **根本不动现有程序**，直接报错。
- 替换之后失败（install.sh 非 0、健康检查不过）→ 还原源码快照并重建，作业记 `failed`。
- 只保留最近 2 份源码快照，避免吃满磁盘。
- 后台**持久横幅**显示「升级失败，已自动回滚」+ 可看日志（PRD 要求：半夜炸了人不在终端前，
  系统必须自己喊出来，且不能阻塞经营操作）。

### 4. 更新源是可配置的，不绑死某个发布服务器

`GET <update_source_url>` 返回：

```json
{
  "version": "1.1.0",
  "built_at": "2026-11-11T12:00:00Z",
  "commit": "abcdef1",
  "notes": "修复了…",
  "tarball_url": "https://…/mall-1.1.0.tar.gz",
  "sha256": "…"
}
```

拉不到清单**不报错**，返回 `reason` 让界面显示「无法检查」——一次网络抖动不该变成 500。
升级是破坏性操作，必须显式 `confirm: true` 才受理。

### 5. 版本身份是「代码属性」，每次安装刷新

`APP_VERSION` / `APP_COMMIT` / `APP_BUILT_AT` 由 `install.sh` 写入 `.env`，
compose 传给 API。它们描述的是**当前装的这份程序**，所以每次安装都要覆盖写。
只有 `SRC_DIR` / `UPDATER_TOKEN` 这类机器属性才「只补不覆盖」。

## 后果

**收益**

- 商家在后台就能升级，不用碰终端；失败自动回滚，不会留下半死不活的状态。
- 更新源可换：官方源、私有源、甚至内网源，协议一样。
- 升级过程全程可见（进度条 + 日志），出事有据可查。

**代价与风险**

- 宿主上多一个常驻进程，且它能操作 docker 与源码目录——这是「真一键」绕不开的权限。
  靠 `UPDATER_TOKEN`（64 位随机、常量时间比较）+ 只暴露 agent 端点来收窄面。
- 升级期间商城有数十秒不可用（镜像重建 + 容器重启）。这是 Docker 自部署的固有成本。
- 代理自升级时不能重启自己（`MALL_UPDATER_SELF=1`），新脚本要等下次重启才生效。
- `.env` 里的密钥跨升级保留；若 `ENCRYPTION_KEY` 变更，已加密的 SMTP 密码需重填。

## 不做

- 不做灰度发布 / 蓝绿部署——单商户单机，那是给自己找事
- 不做自动升级（无人值守换版本）：升级必须人点确认，且二次确认
- 不做多机编排、集群滚动更新
- 不做从应用内上传任意包执行（等于开一个远程执行入口）

## 真机演练口径（Instabox admin-one，2026-11-11）

```
造 1.0.1 包 + 本地更新源 → 检查更新（has_update）
→ 一键升级（备份 → 校验 → 替换 → install.sh → 健康检查）
→ 版本号变 1.0.1、商品/订单数量不变、健康 ok、代理仍在线
→ 坏校验和包 → 作业 failed、原因点名「校验失败」、程序仍是 1.0.1
```
