# ADR-058：订单「再买一次」

- 日期：2026-11-13
- 状态：已采纳
- 关联：ADR-042（评价，同一处「订单行 → 商品动作」）、ADR-048（收藏）

## 背景

复购是电商最高频的动作。现在的路径是：我的订单 → 记住商品名 → 去搜索 → 找到商品页 →
重新选规格 → 加购。五步，其中「重新选规格」最容易选错。

淘宝在订单详情和订单列表里都有「再次购买」：点一下，商品直接进购物车。
我们缺这一步，等于把最容易做的复购推给顾客自己拼。

## 决策

### 1. 加购用**变体 id**，不是商品 id

购物车按变体管理：同一商品「黑色」「白色」是两个变体，价格可能不同。
拿 productId 加购，后端会当成不存在的变体，或者把两个规格算成一件。

所以先把 `line_items.variant_id` 映射进订单视图（`OrderLineSnapshot.variantId`）——
改造前只映射了 productId（评价用），加购拿不到变体。这是本 ADR 的前置修复。

### 2. 历史订单：跳过并**如实告知**，不静默少加

改造前落库的订单行快照里没有变体 id。这类行加不进来，界面上必须说
「另有 N 件规格信息不全，请到商品页重新选择」。

静默跳过是最坏的处理：顾客以为三件都加进去了，结账时才发现少一件。

### 3. 数量沿用订单里的数量

一单买过 2 件，再买就是 2 件。淘宝同做法。
顾客要改成 1 件，购物车里改一下比从 0 开始加更省事。

### 4. 措辞不承诺「都加好了」

加购是乐观更新（本仓购物车的一贯做法）。缺货的那件要等服务端返回才会被回退，
所以文案写「已加入购物车；缺货商品会自动移出」，而不是「已加入 3 件」。

### 5. 位置：订单详情、金额下方

顾客看完「这单花了多少」，紧接着才是「再来一单」。
不放页头：页头是状态与订单号，塞动作会把「这单现在怎么样」冲淡。

订单列表暂不加：列表每行已经有「查看」，再加一个高频写操作容易误点。

### 6. 演示数据补上变体 id

mock 的三笔示例订单现在指向 mock 目录里真实存在的变体
（`var_hp_black` / `var_kb_brown` / `var_pb_blue`），
否则演示模式里这个按钮永远不出现，等于没做。

## 后果

- 店面 `lib/checkout.ts`：`OrderLineSnapshot.variantId`、`toOrderRecord` 映射 `variant_id`
- 店面 `lib/orders.ts`：`buyAgainLines(order)` 纯函数（返回 `lines` + `skipped`）
- 店面订单详情：金额下方「再买一次」按钮 + 结果说明；示例订单补变体 id
- 无 API / 模块 / 迁移改动（`line_items.variant_id` 一直在返回，只是前端没用）
- 测试：storefront +5（按变体输出、历史行跳过计数、全无变体不出行、
  live 映射带出 variantId）；既有「订单状态映射」用例同步断言 variantId

## 遗留

- **订单列表的「再买一次」**：需要列表接口也带 line_items（已带），但按钮密度与误点风险要单独权衡
- **缺货时「到货提醒」**：现在缺货只能在购物车里被回退，没有「到货通知我」的登记入口，
  是下一个要补的闭环
- **价格变化提示**：再买一次按**订单历史价**加购，购物车会以当前价重算。
  差价大时应该提示一句，需要商品当前价一起比对
