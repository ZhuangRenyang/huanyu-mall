# ADR-056：后台订单按日期筛选

- 日期：2026-11-13
- 状态：已采纳
- 关联：ADR-031（服务端筛选）、ADR-052（批量发货）

## 背景

订单列表能按状态筛、能按订单号/邮箱搜，但**不能按日期筛**。

商家的实际动作几乎都带时间：核对昨天发出去的货、导出本周的流水、
只给今天的单批量发货。没有日期筛选，只能一页页翻到底再自己数。

淘宝「已卖出的宝贝」上方就有一条时间条：今天 / 近 7 天 / 近 30 天 / 自定义。

## 决策

### 1. 只收 `YYYY-MM-DD`，按**店铺本地日**解释

`from` 取当天 `00:00:00.000`，`to` 取当天 `23:59:59.999`。

不让前端传时间戳：那样「今天」按谁的时区算说不清。商家在深圳开店，
用 UTC 切日会凭空少掉 8 小时的单 —— 这类差异在对账时最难查。

格式不对直接 400（`from=2026/11/01` 这种写法不允许），
而不是静默忽略 —— 静默忽略等于「筛了但没筛」，商家会以为当天真的没单。

### 2. 用 `created_at` 而不是 `placed_at`

两者通常相同，但 `created_at` 一定有值（NOT NULL DEFAULT now()），
历史数据里 `placed_at` 可能为空。按 `placed_at` 筛会把这些老订单永远漏掉。

### 3. 筛选条件进仓储，不在内存里过滤

`OrderQuery.createdFrom/createdTo` → SQL `gte/lte`。
与 ADR-031 同一条纪律：拉一页再本地筛，订单一多就静默漏。

### 4. 页签角标**不随日期变**，并在界面上写清楚

`counts` 是「全店还有多少单要处理」，随筛选变会让商家以为待发货真的少了。
底部文案改成两个口径分开写：

> 筛选结果 12 笔　全店：待发货 5 笔 · 退款中 1 笔

### 5. 切换时间范围清空勾选

与换页签/翻页同一条纪律（ADR-052）：不然会出现「对看不见的订单批量发货」。

## 后果

- order 模块：`OrderQuery.createdFrom/createdTo`、仓储 `gte/lte`
- API：`GET /admin/orders?from=&to=`（`YYYY-MM-DD`，非法 400）
- 后台：订单页时间条（全部/今天/近 7 天/近 30 天/自定义两个日期），
  底部计数明确「全店口径」
- 无迁移：`created_at` 一直有值，现有索引 `idx_order_status` 之外未加时间索引
  （单店订单量下顺序扫可接受；真到十万级再补 `(created_at)`）
- 测试：api +2（范围覆盖今天命中 / 未来与过去为空；格式错误 400）

## 遗留

- **导出**：按日期筛完后「导出这批」是自然的下一步，需要 CSV 生成（金额/地址/单号），
  与纸质对账配合，另做
- **按发货时间/付款时间筛**：本期只做「下单时间」。发货时间要 join fulfillment，
  付款时间要看 payment，口径各不相同，等有明确需求再加
- **时区**：当前一律按服务进程的本地时区解释。多时区店铺需要在
  channel/settings 上存 `timezone`，再按它切日
