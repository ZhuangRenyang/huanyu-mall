# ADR-004: 事件总线与队列 = 进程内 EventBus + outbox + BullMQ（不用裸 Redis Streams）

## Status: Accepted (2026-11-08)

## Background

铁律 6：事件分两层——进程内 Event Bus + Subscriber 解耦；对外 Webhook 投递层单独建（二期）。一期要求（PRD M12）"进程内事件 + Redis 持久化队列，保证重启不丢在途任务"。候选：裸 Redis Streams 自研、BullMQ（基于 Redis 的成熟队列库）、两者分层、纯进程内（PM 坑 1 明确指出不能留 in-memory 默认）。

关键事实：Medusa 默认 event-bus/workflow-engine/locking 是 in-memory 实现，容器重启会丢在途流程（竞品真实踩坑）。本项目的铁律 9（一键安装）意味着**必须重启不丢**，所以一期就必须上持久化。

## Decision

采用「分层」：

1. **进程内 EventBus**（`core/event`）：模块间发事件解耦用 `emit()` + 同步 subscriber，同一进程内毫秒级。**但 emit 不直接触网**，而是写 `event_outbox` 表（与业务事务同库同事务，保证不丢）。
2. **outbox → BullMQ**：一个轻量 outbox 泵轮询 `event_outbox`，把已提交事件投递到 BullMQ 队列（`event-dispatch`），worker 消费后调用对应 subscriber。崩溃时 outbox 表里的未投递记录会被重投（至少一次投递，subscriber 须幂等）。
3. **BullMQ 6.7.2** 作为唯一队列实现，承载 `payment-webhook`/`order`/`image`/`search-index`/`mail`/`scheduler` 六个队列（§10.3）。

**不用裸 Redis Streams 的原因**：Streams 是原始数据结构，需要自己实现消费组、ack、重试、死信、定时任务、可视化——BullMQ 全都有且成熟。自研 Streams 相当于重造一个更差的 BullMQ。

## Consequences

正面：
- 重启不丢（outbox 同事务落库，BullMQ 基于 Redis 持久化）。
- 至少一次投递语义明确，subscriber 幂等是显式要求（写进 §5 的测试规范）。
- 二期对外 Webhook 投递层直接复用 outbox + 独立 `webhook-dispatch` 队列，不需要重做。

负面：
- 比纯进程内多一张 outbox 表 + 一个泵，运维多一个关注点。
- 至少一次投递意味着 subscriber 必须幂等（多写一条死信记录可接受，重复扣款不可接受——所以支付回调**不走 event-bus**，走专用 `payment-webhook` 队列 + workflow 幂等）。
- 事件顺序不保证（BullMQ 按 job 并发，同一实体的多个事件可能乱序），需要靠 subscriber 幂等 + 版本号兜底。

## Alternatives

1. **裸 Redis Streams 自研**：无第三方队列库，但需自实现 ack/重试/死信/定时，成本高、易漏边界。否决。
2. **纯进程内（对齐 Medusa 默认）**：实现最简，但违反"重启不丢"，PM 坑 1 已证明是真实事故源。否决。
3. **引入 Kafka/RabbitMQ**：能力最强，但增加一个重基础设施容器，违背铁律 9"一键安装命令数为 1、必填配置为 0"，且单商户规模用不上。否决。
