# ADR-007: 认证 = JWT(15m) + Refresh 轮换(7d/30d) + Redis 黑名单 + RBAC 两档

## Status: Accepted (2026-11-08)

## Background

简报要求覆盖 Store 端客户与管理后台 RBAC。铁律 9 要求一键安装零配置、必填配置恒为 0，这排除了"外部 OAuth 强制"（微信 OAuth 需服务商资质、短信需短信服务商，均违反零配置）。候选：纯 JWT + refresh、session + Redis、混合。

## Decision

采用**混合**：JWT 短命 access + 可撤销的 refresh 轮换 + Redis 黑名单。

- **access token**：JWT，有效期 15 分钟，无状态（不查库），payload 只放 `{ sub, scope, roles }`。
- **refresh token**：不透明随机串（非 JWT），Store 端 30 天、Admin 端 7 天，**轮换**（每次 refresh 返回新对，旧 token 立即失效）；哈希值存 Postgres `refresh_token` 表（可审计、可批量撤销），撤销的黑名单 jti 写 Redis（毫秒级校验）。
- **RBAC 两档**：`admin`（全部权限）、`staff`（除"设置/密钥/用户"外全部），权限在 `rbac_role`/`rbac_user_role` 表，路由显式声明 `permission`，未声明视为配置错误（启动 fail-fast）。
- **Store 匿名**：用 `x-publishable-key` 解析 channel，匿名可读 + 游客下单；登录后 `customer_id` 归属校验兜底越权。
- **密码哈希**：argon2id（`memory=19456, iterations=2, parallelism=1` 的 OWASP 基线）。

## Consequences

正面：
- 无外部依赖、零配置，满足一键安装。
- refresh 轮换 + 黑名单 = "可撤销的 JWT"，兼顾无状态与安全性。
- access 短命限制了令牌泄露的爆炸半径。

负面：
- 轮换带来并发刷新竞态（§16 坑 13），需"单飞"处理：同 refresh token 并发刷新只发一对新 token。
- 需要 refresh_token 表 + Redis 两层状态，比纯 JWT 多两张表。
- 多实例下 access 无状态是优点，但 refresh 撤销依赖 Redis，需保证 Redis 可用（Redis 挂时降级为"允许 access 到期后重新登录"，不阻塞新登录）。

## Alternatives

1. **纯 JWT（长命 access + 短 refresh，无黑名单）**：最简，但无法立即撤销（退出登录/改密后旧 token 仍有效到过期），安全风险不可接受。否决。
2. **session + Redis（全有状态）**：可即时撤销，但每个请求都要查 Redis，且 Redis 挂则全员掉线，单点风险高；与"access 无状态"的轻量诉求冲突。否决。
3. **纯 JWT 长命（无 refresh）**：体验最差，令牌过期频繁登出，且长命令牌泄露风险最大。否决。
