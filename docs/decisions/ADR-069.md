# ADR-069：到货提醒的有效期与重新登记

- 日期：2026-11-13
- 状态：已采纳
- 关联：ADR-059（到货提醒）、ADR-060（库存页等货人数）

## 背景

ADR-059 做完了到货提醒的闭环，但留下两个洞：

1. **登记永久有效**：淘宝的到货提醒有期限。不设期限的话，三个月后补货还会给
   一条半年前的登记发信，那封信在顾客眼里是莫名其妙的骚扰。
2. **重新登记是白登记**：ADR-059 文档写「通知过后顾客重新登记，下一次补货还能再收到一封」，
   但实现里重复登记走的是 `onConflictDoNothing` —— 老记录的 `notified_at` 仍置位，
   而待通知查询只取 `notified_at IS NULL`。于是**顾客重新点了提醒，却再也不会收到任何邮件**。

第 2 条是文档与实现不一致，属于真实的漏发，不是设计选择。

## 决策

### 1. 有效期 30 天，过期即失效

`STOCK_ALERT_TTL_DAYS = 30`（导出于 product 模块，接口与前台共用一个数，不各写各的）。

规则：`created_at` 在 N 天内的登记才算「还在等通知」。
超过就不通知、也不计入后台的「N 人等货」热度 —— 三个月前的需求不该占用今天的补货优先级。

### 2. 有效期在**服务层**过滤，不写进 SQL

`listPendingStockAlerts` 取回待通知行后按 `created_at >= since` 过滤；
`countPendingStockAlerts` 直接由这个列表计数，**两个口径天然一致**（不会再出现
「列表 3 条、角标 5 人」这种对不上的情况）。

放服务层而不是 SQL 的理由：规则只有一条（时间窗），放服务层能用确定性的纯逻辑测；
提醒条数极少，内存过滤不构成负担。

仓储层的 `countPendingByVariantIds` 随之删除 —— 计数口径只有一处。

### 3. 重新登记 = 重新排队

`upsert` 从 `onConflictDoNothing` 改成 `onConflictDoUpdate`：

- `created_at` 置为当前时间 → 有效期重新起算；
- `notified_at` 清空 → 之前发过「到货了」，这次补货还能再收到一封。

这正是 ADR-059 文档承诺的行为，现在实现与文档一致了。

### 4. 接口回带有效期截止时间

`POST /store/stock-alerts` 返回 `expires_at`，前台直接显示「有效期至 X」，
不自己算天数 —— 前端复制一份 30 天就会和后端漂移。

## 后果

- product：`STOCK_ALERT_TTL_DAYS` / `stockAlertSince`（服务）、
  `listPendingStockAlerts` 加有效期过滤、`countPendingStockAlerts` 改由列表计数、
  仓储 `upsert` 改为冲突即刷新（并删掉 `countPendingByVariantIds`）
- API：`POST /store/stock-alerts` 返回 `expires_at`
- 店面：登记前说明「登记 30 天内有效」，登记成功显示「有效期至 X，过期后重新登记即可」
- 测试：product +4（有效期内可通知、超期不再通知也不再计热度、重新登记重新排队、
  29 天在内 / 31 天不在的边界）、api +1（返回 expires_at 且约等于 30 天）
- 无迁移（有效期是规则不是数据，不落库）

## 遗留

- **过期记录清理**：现在只是「不通知」，老记录还留在表里。数据量大了要定期清理，
  但那是一次性维护动作，不适合放进请求路径
- **有效期可配置**：现在写死 30 天。淘宝按品类不同（手机 vs 家具），要做的话应放进
  店铺设置，由配置项驱动而非常量
- **失效提醒**：到期前给顾客一封「你等的商品快过期了」需要邮件调度，属通知模块扩展
