# ADR-015 订单履约状态：部分发货 + 发货后自动推进

- 日期：2026-11-11
- 状态：Accepted
- 范围：订单状态机、履约事件、后台/店面状态展示

## 背景

一期把「发货」实现成了只写运单：`addShipment` 提交库存预留、更新发货单状态，
但**从不调用 `order.transition`**。结果是：后台填了运单、货都发走了，订单仍是「待发货」。

多仓拆单上线后问题放大：一个订单可能有两张发货单，发完一张、另一张还没发，
而状态机里根本没有「部分发货」这个状态。

已核实：

1. `state-machine.ts` 只有 `paid → fulfilled`，没有中间态。
2. `fulfillment` 模块不发事件，订单侧无从知道「发了多少」。
3. `FulfillmentDTO` 不含行项，无法按订单行汇总已发数量。

## 决策

### 1. 状态机增加 `partially_fulfilled`

```
pending → awaiting_payment → paid → partially_fulfilled → fulfilled → delivered
                                   ↘ refunded（paid/partially/fulfilled 都可退）
```

`partially_fulfilled` 的语义：**至少一个仓已发货，但订单行未全部发完**。
单独建了发货单但还没填运单，不算已发。

### 2. 发货后由事件驱动推进，不在路由里写业务

- `addShipment` 成功后发 `shipment.created`（携带 `orderId`、`fulfillmentId`）。
- `workflows` 订阅者计算：按订单行汇总所有 `status = shipped | delivered` 的发货单行项数量。
  - 全部行项发完 → `fulfilled`
  - 发了一部分 → `partially_fulfilled`
  - 一件没发 → 不推进
- 只处理 `paid` / `partially_fulfilled` 的订单；已取消、已退款不动。
- 幂等：同状态迁移直接返回；事件重放不会重复推进。

### 3. 展示口径

- 后台订单列表：新增「部分发货」筛选与计数；详情时间线把部分发货视为「已发货」。
- 店面：`partially_fulfilled` 按「已付款」展示，不能落到 `processing`。
- 发货计划接口继续负责「还差哪个仓」；状态负责「这单到哪一步」。

## 后果

**收益**：订单状态与事实一致；客服能一眼看出「发了一半」；后续订单通知可以直接挂在状态变化上。

**代价与风险**：

- 状态多了一个，所有穷举 `OrderStatus` 的地方都要补（已同步 SDK、后台类型、店面映射）。
- 事件是异步的：极端情况下「运单已填、状态未推进」有毫秒级窗口；刷新即可恢复，不影响资金。
- 若发货单行项与订单行不一致（数据异常），汇总可能偏小；发货计划的 `unmatched_quantity` 是同一类问题的探针。

## 不做

- 不做「按行部分发货」（一行拆两次发）——一期发货数量必须等于该行数量。
- 不做自动确认收货；`delivered` 仍由后台/物流回调推进。
