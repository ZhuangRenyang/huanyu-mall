# ADR-055：顾客自助改密

- 日期：2026-11-13
- 状态：已采纳
- 关联：ADR-025（注册方式）、ADR-027（忘记密码）、ADR-029（会话撤销）

## 背景

顾客想换密码，只有一条路：**忘记密码** —— 输入账号 → 收验证码 → 重设。

这条流程本来是给「密码丢了」用的。记得密码的人想换个更安全的，
却被逼着先证明「我丢了密码」，而且强依赖邮件/短信通道可用：

- 店铺没配 SMTP 时，邮箱注册的顾客**完全无法改密**（通道报错直接返回）；
- 验证码有频率限制，改一次密码要等冷却；
- 客服收到的「我要改密码」全都变成一次人工重置。

管理员那边早在 ADR-027 就有自助改密（`changeAdminPassword`），顾客没有——
同一件事两套待遇，只因为顾客侧当时没做。

## 决策

### 1. 与管理员改密共用一套实现，只多一个 `scope` 参数

`change-password.ts` 抽出 `changePassword(deps, input, expectedScope)`：

- `changeAdminPassword` → `scope: 'admin'`
- `changeCustomerPassword` → `scope: 'customer'`

`expectedScope` 是安全边界：**顾客 token 改不了管理员口令**（反之亦然）。
不共用会分叉成两套规则，总有一天只有一处记得撤销会话。

### 2. 身份只认 token，`identityId` 不从 body 取

`identityId = req.auth.sub`。body 里传 `identity_id` 一律无效（zod 非 strict，
多余字段被丢弃）—— 接受它等于「传谁的 id 就改谁的密码」，最典型的越权。

### 3. 四道校验，顺序固定

1. 登录态（`customerAuth` 是可选鉴权，必须自己判 scope）；
2. 当前口令正确（否则 401 `invalidCredentials`，不区分「身份不存在」与「密码错」）；
3. 新口令强度（`checkPasswordStrength`，至少 8 位）；
4. 新旧不同（与当前口令相同直接拒）。

### 4. 成功后撤销该身份全部会话，包括当前这台

密码变了旧会话必须立刻失效，否则「改密」对已登录的设备毫无影响 —— 等于没改。

因此前端在成功后**顺手清本地登录态**并把顾客踢回登录页：
不清的话页面仍显示「已登录」，下一次请求才 401，顾客会以为页面坏了。

### 5. 不放「重置密码」的验证码通道

知道旧密码就不需要验证码。要求验证码等于把两件事混在一起，
还让「通道没配」重新变成改密的阻塞项。

## 后果

- auth 模块：`changePassword` 内部函数 + `changeCustomerPassword` 导出；
  `IAuthModuleService.changeCustomerPassword`
- API：`POST /store/auth/password/change`（200 返回 `revoked_refresh_tokens`；
  401 未登录或旧密码错；400 弱口令/与原口令相同）
- SDK：`changeCustomerPassword`
- 店面：`lib/account.ts` 的 `changePassword`（成功后 `clearSession`）、
  `components/account/security-settings.tsx`、账户页末尾「账号安全」卡片
- 测试：api +5（401 匿名、旧密码错 401、弱口令 400、与原口令相同 400、
  成功撤销会话且旧密码失效、body 传 identity_id 无效）

## 遗留

- **改密后的通知邮件**：「你的密码已修改」是账号安全的标准告知项，
  需要 notification 模板 + 事务性 outbox，与「新设备登录提醒」一起做更合适
- **手机号换绑**：顾客资料里的手机号目前只能注册时确定，换号需要验证码双验证，另做
- **登录设备列表**：能看「在哪几台设备登录、单独踢下线」需要 refresh_token 的 UA/IP 留痕
