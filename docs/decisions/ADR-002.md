# ADR-002: 自研「顺序步骤 + 补偿栈 + journal」Workflow 引擎

## Status: Accepted (2026-11-08)

## Background

铁律 3 是硬约束：跨模块流程只走 Workflow 引擎编排，每步必须定义 compensation 补偿回滚，禁止业务代码手写跨模块事务。这是全项目最高风险项。候选：复用 XState（成熟状态机，但为"状态机"设计而非"跨模块 saga 编排"，且引入其 v5 语义）、事件溯源（Event Sourcing，正确性最强但成本极高）、自研最小引擎。

关键取舍点（来自 Medusa 源码形态）：Medusa v2 的 `createWorkflow` 是**声明式 DAG**——`input` 是惰性代理、`transform()` 声明依赖、`parallelize()`/`when()` 组合（证据：`packages/core/core-flows/src/order/workflows/create-order.ts` 内 6 处 `transform`、1 处 `parallelize`、2 处 `when`）。这套机制换来并行与声明式重放，但类型体操重、自研成本 ≥ 2 周。一期下单/支付/退款/发货**不需要并行步骤**。

## Decision

自研「**顺序步骤 + 补偿栈 + 步骤日志（journal）+ 重放（replay）**」命令式引擎（约 700–900 行）：

- 四个原语：`createWorkflow`、`ctx.step(step, input)`、`StepResponse(output, compensateInput)`、`StepResponse.permanentFailure()`。
- `ctx.step()` 是唯一副作用入口，实现「run-or-replay」：已完成步骤直接返回 journal 里的 output（崩溃恢复安全）。
- 补偿栈按 `seq DESC` 倒序执行，幂等、可重试；补偿自身永久失败 → 状态 `compensation_failed` + 死信 + 告警，保留现场交人工。
- 三层幂等：API 层 `Idempotency-Key`、引擎层 `(workflow_id, idempotency_key)`、步骤层 `${executionId}:${stepId}`（并透传给支付网关，§5.6）。
- **明确不做**：`parallelize`、声明式 `transform`（普通 TS 即可）、`when()` 原语（`if` 即可）、hook 机制（二期用 subscriber + 自定义 step 实现同等能力）、事件溯源。

完整实现草案见 ARCHITECTURE.md §5（含状态机、三张内核表、引擎核心循环伪代码、补偿语义 R/X/I 三类、测试三层）。

## Consequences

正面：
- 成本降到对齐 Medusa 声明式方案的约 1/4，8 个工作日可控。
- 命令式模型普通 TS 工程师能读懂、能排错（错误栈直白，无惰性代理魔法）。
- journal + replay 天然获得"崩溃可恢复、可重放"，满足一键升级/重启不丢在途流程的要求。
- 补偿可跨进程恢复（补偿函数只依赖 `compensateInput`，不依赖内存状态）。

负面：
- 无并行能力：一次下单里"查渠道 + 查客户 + 查区域"这类无依赖读取只能串行（一期延迟可接受，毫秒级）。
- 重放依赖业务代码确定性：若 step 内写死 `Math.random()` 或读取当前时间，重放会不一致（用 §16 的确定性纪律约束，随机数与时钟走 `ctx` 注入）。
- 无事件溯源审计：只能回答"现在是什么状态 + 每步历史"，不能回答"任意时刻的全量快照"（一期不需要）。

## Alternatives

1. **XState 5.33.4**：成熟、有可视化，但它是"有限状态机/状态图"抽象，而我们要的是"带补偿的跨模块 saga 编排 + 持久化 journal"；硬套会为了用 XState 而把补偿塞进 action，持久化与恢复还得自己搭，收益为负。否决。
2. **事件溯源（Event Sourcing）**：正确性与可审计性最强，但需要事件存储、投影、快照、重放基础设施，成本 ≥ 3 周，且与"一期 4–8 周"严重冲突。否决。
3. **照抄 Medusa 声明式 DAG**：能力最全，但自研成本 ≥ 2 周、类型体操极重、排错难，一期用不上并行。否决（二期若确需并行，可作为引擎 v2 演进方向）。
