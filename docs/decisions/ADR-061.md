# ADR-061：退货地址快照

- 日期：2026-11-13
- 状态：已采纳
- 关联：ADR-051（退货退款）、ADR-053（店铺退货地址）

## 背景

ADR-053 把退货地址做成**店铺配置**：一处填写、同意退货时带给顾客。好处是低频改、全店唯一。

但它同时留下一个洞：顾客看到的是**实时读取**的当前配置。

```
周一 商家同意退货，顾客被指向「深圳南山 3 号仓」
周二 商家搬仓，把店铺地址改成「东莞松山湖 8 号仓」
周二 顾客打开页面 → 看到东莞，按东莞寄出
周三 商家的收货人还在南山等，包裹消失在两个地址之间
```

地址在「同意退货」那一刻就是**承诺**。承诺必须留痕，不能跟着设置一起漂。

## 决策

### 1. 同意退货时把地址快照进单据

`refund_request.return_address`：同意那一刻把店铺配置的地址复制一份。

- 顾客看到的永远是**当初被告知**的那个地址（附一行「之后改动店铺设置不影响本单」）；
- 商家在售后单里能查「这单当时让寄到哪」，不必靠记忆或翻聊天记录。

### 2. 快照由调用方（路由）写入，服务层不认识 theme

`POST /admin/refund-requests/:id/agree-*` 里读 `theme.getSettings()`，把 `return_address`
作为参数传给 `agreeReturnRequest(id, { reviewNote, returnAddress })`。

order 模块只负责**存与取**。跨模块取值留在组合根附近，模块依赖图不多一条边
（`check:module-graph` 仍然全绿）。

### 3. 允许为空，不因此拦住同意

商家没配地址也能同意退货 —— 否则退款会永远卡在「待处理」，顾客的钱退不出去。
此时快照为 `null`，顾客端提示「联系客服获取地址」，与 ADR-053 的降级一致。

**但要提前提醒**：后台「同意退货」弹窗现在会显示「买家看到的退货地址」，
未配置时直接红字警告「这单会卡在待寄回」。让商家在点下去之前就知道。

### 4. 空白按「没配」存 null

`"   "` → `null`，与店铺资料其他字段同一口径。前端只需判一种空。

### 5. 前端优先用快照，店铺当前配置只作兜底

`active.returnAddress ?? returnAddress`：老单据（ADR-061 之前同意的）没有快照，
仍能用当前配置显示，不至于空白。

### 6. 仅退款不写地址

没货要寄，记一个地址反而误导。快照只在退货退款路径写入。

## 后果

- order：迁移 `0009_return_address_snapshot.sql`（`ADD COLUMN`，无破坏）、
  模型 `returnAddress`、`RefundRequestDTO.return_address`、
  仓储 `updateRefundRequest({ returnAddress })`、
  `agreeReturnRequest(id, opts)` 签名从 `(id, reviewNote?)` 改为对象参数
- API：`/admin/refund-requests/:id/approve` 的退货分支读设置并快照
- 店面：退款视图带 `returnAddress`；「待寄回」卡片优先显示快照并注明「之后改动不影响本单」
- 后台：退款行显示「寄往：<首行>」；同意退货弹窗预览将要快照出去的地址，未配置时红字警告
- mock：同意退货时从 `admin:store-profile` 读地址快照，演示里也复现得出「老单不变」
- 测试：api +4（写入并可读、改设置后老单不变、未配置也能同意、仅退款不写地址）、
  order +1（写入与空白转 null）

## 遗留

- **退货地址多处**（多仓/多退货点）：现在全店一个。真要做需要「退货地址库 + 商品/订单选址」，
  与 ADR-021 的运费模板同构，工作量不小
- **买家自填退货地址的场景**（换货、上门取件）：属于换货流程，不在退款链路里
- **快照的展示位置**：现在只在退款行与顾客卡片。发货单/售后打印单是否需要印「退货寄往」，
  等有商家反馈再加
