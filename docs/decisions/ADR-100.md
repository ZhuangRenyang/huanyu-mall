# ADR-100：拼团——参团免费、成团领券，不产生任何无人值守的资金动作

- 日期：2026-11-14
- 状态：已采纳
- 关联：ADR-078（D 期营销）、ADR-023（不做自动退款）、ADR-029（领券）、ADR-099（秒杀）

## 背景

ADR-078 把拼团列入 D 期。但拼多多式的拼团是「先付款 → 等人凑齐 → 未成团自动退款」，
这与 **ADR-023「退款只走人工审核」** 直接冲突：未成团必须自动退，否则钱白收；
自动退又违反「不存在无人值守就会退钱的路径」。

这个冲突不能靠「加一个例外」绕过 —— 一旦开了「特定场景自动退款」的口子，
后面所有场景都会援引它。

## 决策

### 1. 拼团 = 参团免费，成团后领券

```
浏览活动 → 参团（不收款/不建订单/不占库存） → 人齐成团 → 每人领「拼团专享券」 → 拿券正常下单
```

未成团时**什么都没发生**：没有收过钱，也就没有退款。拼团因此不新增任何
资金链路，与 ADR-023 完全兼容。

代价是「不能立刻锁定成交」—— 顾客成团后仍可能不下单。对单商户来说，
这个代价远小于「自动退款」带来的资损与对账风险。

### 2. 拼团价由「拼团专享券」承载

创建活动时**自动建一张券**（同模块内调用，不跨模块）：

| 字段 | 值 | 理由 |
|---|---|---|
| type | `specific_product` | 只对该商品生效 |
| discount_type / value | `fixed` / 原价 − 拼团价 | 差价即优惠额 |
| min_spent | 原价 | 买 2 件只减 1 份差价，不会「每件都打折」 |
| is_public | `false` | 不出现在店铺券列表，否则谁都能领 |
| collect_limit | 1 | 每人一张 |
| scopes | 该商品（product） | 券范围只到商品级（券模块没有变体级范围） |
| ends_at | 活动结束 + 7 天 | 成团可能发生在最后一刻，留出用券窗口 |

用券承载拼团价的另一个好处：核销、退款、对账全部走既有链路，**零新增资金逻辑**。

### 3. 「自助领取」与「系统发放」分开

原 `collectVoucher` 强制 `is_public`（顾客自助领店铺券）。拼团券是系统发，
不能走这条路。因此拆成：

- `collectVoucher`：保留公开性校验（店铺券）→ 内部调 `issueVoucherToCustomer`；
- `issueVoucherToCustomer`（private）：只校验状态/有效期/限领，供拼团成团后发放。

领券资格由**团**决定：必须「我参了团 + 我的团已成团」，否则拼团就退化成
「谁都能领的券」。

### 4. 团人数用条件 UPDATE，防并发超员

`group_buy_team.member_count` 存在团上，占名额只有一条语句：

```sql
UPDATE group_buy_team SET member_count = member_count + 1,
       status = CASE WHEN member_count + 1 >= team_size THEN 'success' ELSE status END
WHERE id = ? AND status = 'forming' AND member_count < team_size
```

返回 0 行 = 这个团刚被抢满 → 换下一个团。先查后写必然在并发下超员。
`team_size` 在开团时快照到团上：活动后来改人数，已开的团仍按当时规则走。

### 5. 过期惰性判定，不引入定时任务

团队 `expires_at` = 活动结束时间。读到「过期未满」的团时就地置 `expired`
（`listMyGroupBuys` / 领券 / 重复参团时触发）。没有后台定时任务，
状态只在被访问时收敛 —— 与秒杀的活动时间窗同一套思路。

### 6. 一人一活动只能在一个团

`group_buy_member` 有 `unique(team_id, customer_id)`；服务层在参团前先查
「我在这个活动里的团」，有就返回原团（`joined=false`）。重复点「参团」不报错。

## 后果

- promotion：迁移 `0015_group_buy.sql`（三表 + 唯一索引 + CHECK）、模型
  `groupBuy / groupBuyTeam / groupBuyMember`、DTO、仓储 12 个方法、服务 7 个方法；
  `collectVoucher` 拆出 `issueVoucherToCustomer`
- API：`GET/POST /admin/group-buys`、`POST /admin/group-buys/:id/status`（settings 权限）；
  `GET /store/group-buys`、`POST /store/group-buys/:id/join`、`GET /store/group-buys/mine`、
  `POST /store/group-buys/:id/voucher`（后三个需登录）
- SDK：`listGroupBuys / createGroupBuy / setGroupBuyStatus`（后台）、
  `listGroupBuys / joinGroupBuy / listMyGroupBuys / claimGroupBuyVoucher`（店面）
- 后台：营销组「拼团」页（页签 + 新建活动对话框，商品/规格/拼团价/成团人数/时间窗）
- 店面：`/group-buys` 页（参团 / 团进度 / 成团领券 / 券码复制）+ 头部导航
- 测试：promotion +7（自动建券、两人成团补位、重复参团幂等、成团才可领券、
  过期惰性、创建校验、状态机）、api +5（建-上架-店面可见、参团与成团、领券幂等、
  价格校验、我的拼团）；promotion 80、api 360、storefront 46；迁移 68

## 遗留

- **成团后自动下单/自动扣款**：需要退款链路兜底，ADR-023 下不做
- **团详情与邀请分享**：现在只能在列表里看到自己的团，没有「团详情页 + 分享链接」
- **团长权益（团长价/团长免单）**：需要按角色差异化定价，属独立规则
- **过期团的清理**：惰性判定，历史团会一直留在表里（可在维护任务里归档）
- **拼团价与其它优惠叠加**：走券的「多码取折扣最大」规则，天然只抵一张；
  若商家希望拼团价可再叠加满减，需要另定规则
