# ADR-103：会员标签——多对多打标与按标签筛客户，不做分组折扣

- 日期：2026-11-14
- 状态：已采纳
- 关联：ADR-078（E 期会员）、ADR-102（会员等级）

## 背景

CRMEB 的会员体系里有两套东西：**会员分组**（每组一个折扣，互斥）与
**会员标签**（多对多，用于画像与筛选）。

如果两套都做，会出现一个解释不清的问题：同一个客户既在「VIP 组」又有
「高价值」标签，同一件商品按哪个折扣？客服讲不清，顾客更听不懂。

## 决策

### 1. 只做标签，不做分组折扣

- 折扣统一由**会员等级**（ADR-102）承载：按累计消费自动匹配，规则唯一；
- 标签只做**筛选与画像**：多对多，不打折、不互斥。

判断标准：一个能力如果能改变成交价，必须只有一条规则来源。
分组折扣与等级折扣语义重叠，第二个就是重复建模。

### 2. 标签：两表 + 主键去重

`customer_tag`（id/name，名称唯一）+ `customer_tag_link`（customer_id + tag_id 主键）。

主键即去重：重复打标是幂等的，不需要额外判重逻辑。

### 3. 打标是「覆盖式」

`PUT /admin/customers/:id/tags` 传什么就是什么（先删后插，事务内完成）。

不做「增删两条接口」：后台是勾选框，一次提交全部选中项，覆盖式与界面一致；
分成 add/remove 反而要前端算 diff。

不存在的 tag_id 直接忽略（一个脏 id 不该让整次保存失败）。

### 4. 标签筛选必须进 SQL，不在前端过滤

`GET /admin/customers?tag_id=` → 仓储里用 `EXISTS (SELECT 1 FROM customer_tag_link ...)`。

理由：分页与计数用的是同一段条件。若先分页再前端过滤，会出现「这页 20 条只剩 3 条」
和「总数为 0 但明明有匹配」这类错误。

### 5. 客户列表一次批量取标签

`listTagsByCustomerIds` 一次 IN 查询。逐客户查就是 N+1，客户上百后明显卡。

### 6. 删标签同时清关联

先删 `customer_tag_link` 再删 `customer_tag`。反过来会留下指向不存在标签的孤儿行，
筛选与计数都会错。

## 后果

- customer：迁移 `0006_customer_tags.sql`（两表 + 唯一索引 + 关联索引）、
  模型 `customerTag / customerTagLink`、DTO、仓储 8 个方法、服务 5 个方法
- customer 列表：`CustomerListQuery.tagId` + EXISTS 子查询；
  `listTagsByCustomerIds` 批量取标签
- API：`GET/POST /admin/customer-tags`、`DELETE /admin/customer-tags/:id`、
  `GET/PUT /admin/customers/:id/tags`；客户列表 `tag_id` 筛选并下发 `tags`
- SDK：`listCustomerTags / createCustomerTag / deleteCustomerTag / getCustomerTags / setCustomerTags`
- 后台：客户列表页新增标签列、标签筛选、打标对话框、标签管理对话框
- 测试：api +4（创建与重名、打标覆盖式与列表展示、按标签筛选、删标签清关联）；
  api 373、customer 13、cart 30、promotion 89、storefront 46；迁移 72

## 遗留

- **按标签做营销**：按标签发券、按标签定促销都没有；标签目前只用于筛选
- **标签自动规则**：如「30 天未回购自动打标」，需要定时任务或读时计算
- **客户详情里显示标签**：详情抽屉还没拼标签（列表已有）
- **标签分组 / 颜色**：标签多了以后需要视觉分类
- **批量打标**：现在一次只能给一个客户打标，缺少批量选择
