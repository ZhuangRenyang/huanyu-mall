# ADR-028 商品分类：两级类目 + 后台管理 + 店面分类导航

- 日期：2026-11-12
- 状态：Accepted
- 范围：product 模块（分类 CRUD、商品分类关联）、API（`admin/categories`、`store/categories`）、
  admin（商品 → 分类页、商品编辑分类多选）、storefront（商品列表两级筛选）
- 关联：ADR-022（商品图片/批量）、ADR-021（商品域归属）

## 背景

`product_category` 表从一期就在，但**没有任何管理入口**：

| 位置 | 改造前 |
|---|---|
| 后台 | 没有分类页，建不了分类 |
| 商品编辑 | 没有分类项（`POST /admin/products` 支持 `category_ids`，但前端从不传） |
| `PATCH /admin/products/:id` | 没有 `category_ids` 字段 —— 改分类会静默丢 |
| 店面 `GET /store/categories` | 返回硬编码空数组 |
| 店面列表 | 只有「全部商品」一个入口，筛选栏的分类永远是空的 |

结果：顾客没法按类目逛店。这是商品侧最大的结构性缺口 —— 商品再多，
没有分类也只能一页页翻。

## 决策

### 1. 做「分类」，不做「集合」

Shopify 的 Collections 分手动/自动（按价格、标签、厂商规则聚合）。自动集合对单店是过度设计：
商家脑子里已有的概念是「我卖服饰、数码，服饰下面有外套、裙装」，不是「建一条规则把价格 > 100 的商品聚起来」。

所以照淘宝的叫法与结构：**商品 → 商品分类**，两级。

### 2. 只做两级

表上有 `parent_id`，数据库层面支持任意层级，但 UI 与校验限制为两级：

- 一级：服饰 / 数码 / 家居
- 二级：外套 / 裙装（挂在服饰下）

淘宝的多级类目是平台级需求（几亿商品、几千个类目）。自建店铺两级足够，
再加层级只会让商家在后台迷路、让店面的筛选栏变成三行。

规则：二级分类下不能再建子分类（服务层拒绝），分类也不能改成自己的子分类。

### 3. 商品可多选分类，整组替换

淘宝允许一个商品挂多个类目（同一件衣服既是「外套」也在「新品」里）。我们保留同样能力。

更新语义与商品图片一致：**不传 = 不动，传空数组 = 清空，传值 = 整组替换**。
`PATCH /admin/products/:id` 显式映射 `category_ids` ——
不映射就是「保存成功但分类没变」，这个坑在运费字段上已经踩过一次。

### 4. 删除保护：不制造孤儿商品

有商品或有子分类时拒绝删除，并明确告诉商家还剩多少个：

```
该分类下还有 12 个商品，请先把商品移到别的分类
该分类下还有 2 个子分类，请先删除或移走它们
```

软删分类后商品会挂在「不存在的分类」下，店面的分类导航指向空页 ——
比直接报错更难排查。

### 5. handle 自动生成，不逼商家想英文标识

分类的 handle 只用于链接。中文名转不出可读 slug，退回 `cat_<短码>`；
重名自动加 `-2`、`-3`。商家不需要为了一个标识去改分类名。
店面分类页仍用 `?category=<id>`，handle 暂时只作对外稳定标识。

### 6. 店面：一级一行，选中一级后再出二级

筛选栏第一行是一级分类；点中「服饰」后，下面再出一行「外套 / 裙装」。
「全部」在二级行里回到一级本身（而不是清空筛选），否则一级那一行的高亮会对不上。

商品数只统计**上架中**的商品：把草稿算进去会让分类页写着 10 件、点开只有 3 件。

## 后果

- 商品侧从「只有全部商品」变成「能按类目逛」；商家能自己维护类目，不需要开发改代码。
- `ProductDetailDTO` 增加 `category_ids`，后台编辑能回显已选分类。
- 商品保存链路多了一次关联表写入（事务内先删后插），单次操作可接受。
- 分类页还没有独立路由（用 `?category=`）：先满足「能筛」，独立 SEO 页面等有需要再做。

## 不做

- **不做自动集合**（按规则聚合商品）：规则引擎的复杂度远超收益，商家更愿意手动归位。
- **不做三级以上**：平台级需求，自建店铺两级够用。
- **不做分类图片 / 图标 / 描述**：淘宝的类目图是平台统一运营的产物，单店用不上。
- **不做拖拽排序**：排序值输入足够，拖拽要引入 DnD 库并处理键盘可达性。
