# ADR-068：商品列表「销量排序」

- 日期：2026-11-13
- 状态：已采纳
- 关联：ADR-067（商品销量）

## 背景

ADR-067 让商品有了「已售 N 件」，但列表的排序只有「最新上架 / 价格升降序」，
**不能按销量排**。

淘宝的商品列表「按销量排」是默认可用项：卖得好的商品排前面，既是给顾客的
「大家都在买」信号，也是给商家的「哪些货该多备」直觉。没有它，销量这个数就只是
卡片上的一行字，帮不了决策。

## 决策

### 1. 排序键是「已成交销量」，与 ADR-067 同一口径

`sort=sold_count.desc` 按商品级销量（各变体之和）从高到低排。口径不变：
`paid / partially_fulfilled / fulfilled / delivered / completed`，退款/取消/未付款不算。

### 2. 内存排，不推 SQL

销量已经在列表的批量取数里取回来了（ADR-067 同一批 `Promise.all`），
排序直接在内存做，与既有的「价格排序」一致——值都在手上了，再查一次 SQL 是浪费。

真到「全店几万商品 + 销量排序 + 分页」才需要把排序键下推 SQL，那是另一个量级的事。

### 3. 无销量的排最后

`(soldCount ?? 0)` 的降序天然把「没卖出过」的商品沉底。新店/新品不占前列，
把「卖得好的」这个信号让给真正有销量的。

## 后果

- API：`GET /store/products?sort=sold_count.desc` 新增分支
- 店面：列表排序选项加「销量优先」，mock 排序同步支持
- 测试：api +1（`sold_count.desc` 被接受、返回带 sold_count）
- 无迁移

## 遗留

- **排序下推 SQL**：真到商品量级变大、销量排序要跟分页走时，需要把排序键物化或下推
- **「销量 + 价格」复合排序**：淘宝支持多条件，现在一次一个键，够用即可
