# ADR-036 我的订单：状态页签与「按单号查」并存

- 日期：2026-11-12
- 状态：Accepted
- 范围：API（`store/orders` 查询参数）、storefront（订单列表页）
- 关联：ADR-031（后台订单列表同款做法）、ADR-024（顾客账号）

## 背景

店面的「我的订单」改造前是一整条流水账：所有订单按时间倒序堆在一起，
没有状态分组。淘宝的「已买到的宝贝」顶部是一排页签
（全部 / 待付款 / 待发货 / 待收货 / 已完成），顾客找「我那个还没发货的单」靠点页签。

后端其实早就支持按状态查（`listMyOrders({ status })`），前端一次拉了 20 条全量展示，
页签从没做。这类「后端有、前端没用」的缺口，比功能没做更隐蔽。

## 决策

### 1. 页签 = 一组状态，服务端筛

| 页签 | 状态集合 |
|---|---|
| 全部 | 不带 status |
| 待付款 | `pending`, `awaiting_payment` |
| 待发货 | `paid`, `partially_fulfilled` |
| 待收货 | `fulfilled`, `delivered` |
| 已完成 | `completed` |

前端只传页签，服务端按 `statuses` 数组筛。不在前端过滤当前页的 20 条 ——
那会重演后台订单列表踩过的坑（第 21 单永远不出现）。

### 2. 非法状态值忽略，不报 400

`?status=paid,not_a_status` 会被过滤成 `['paid']`。
理由：这个参数是页签传的，多传一个值让整页白屏不值得；
真正的非法调用不会造成数据泄露（归属仍由 token 决定）。

### 3. 保留「按单号查询」

未登录的游客仍可用单号 + 手机后四位 / 邮箱查单（原有能力，不动）。
登录后上面是页签列表，下面是单号查询 —— 淘宝也是「列表 + 订单号搜索」并存。

### 4. mock 与 live 用同一套分组

`ORDER_FILTERS` 同时声明 `statuses`（给服务端）与 `view`（给 mock 本地过滤）。
两套口径写在同一个常量里，避免「演示是一回事、线上是另一回事」。

## 后果

- 顾客能在「待收货」里直接找到要看物流的那单，不用在全部订单里翻。
- 每次切页签发一次请求（20 条/页），比一次拉全量更省。

## 不做

- **不做页签角标计数**：顾客侧不像后台那样需要「有多少单压着」；
  多一个计数就要多一次聚合查询。
- **不做订单搜索（按商品名）**：顾客记得的是单号，不是商品标题。
- **不做「待评价」**：评价功能本身还没做，先不做空页签。
