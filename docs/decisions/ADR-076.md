# ADR-076：后台补「维护」模块（对齐 CRMEB 的四大块之一）

- 日期：2026-11-14
- 状态：已采纳
- 关联：ADR-030（工作台）、ADR-016（邮件 outbox）

## 背景

后台的信息架构此前是：概览 / 商品 / 订单 / 客户 / 营销 / 设置。
对照 CRMEB 后台（装修 / 应用 / 设置 / 维护），我们缺一整块**维护**：

- 数据库、Redis、队列通不通，只有运维跑脚本才知道；
- 邮件发失败会留在 outbox 里，但后台看不到「失败几封」；
- 商家想看「最近谁改了什么」，得去查审计日志接口，界面上没有入口；
- 备份脚本放在 `deploy/scripts/`，界面上没有任何指向。

结果就是：系统出问题时，商家唯一能做的是打电话。

## 决策

### 1. 维护独立成组，不塞进「设置」

判定标准沿用「谁决定什么」：设置决定**店铺怎么卖**（店名、支付、通知、税务），
维护决定**系统怎么活**（探针、队列、日志、备份）。两类读者的关注点也不同。

导航新增「维护」组，位置在设置之后（低频但出事必找）。

### 2. 只读，不做假按钮

CRMEB 的维护有「刷新缓存 / 清除数据 / 在线升级」。本仓：

- 没有页面缓存层（限流用 Redis，但那是基础设施不是页面缓存），
  「刷新缓存」只能做成一个点了没反应的按钮；
- 没有远程升级通道，升级走镜像部署；
- 「清除数据」是不可逆动作，不该出现在一个日常巡检页上。

所以第一版只做四件事：运行状态、邮件队列、数据规模、最近审计。
**放了按钮却点不出效果，比没有这个页面更坏。**

### 3. 探针复用 `/health` 的同一套实现

`checkHealth()` 已经探数据库 / Redis / 队列 / 最新迁移，维护页直接调它，
不另写一份 —— 两套探针迟早给出两个结论。

探针失败时返回 `degraded` 而不是 500：维护页本身不能因为「数据库挂了」而打不开，
那正是最需要它的时候。

### 4. 权限跟审计日志一致（settings）

页面含系统探针与审计流水，属管理员视角；staff 只有订单权限，读不到（403）。

## 后果

- API：`GET /admin/maintenance/status`（探针 + 邮件三态计数 + 订单/商品/客户总数 + 最近 10 条审计）
- SDK：`getMaintenanceStatus()`
- 后台：`/maintenance` 页 + 导航「维护」组
- 测试：api +3（401 / staff 403 / 结构齐全且探针降级不报错）

## 遗留

- **备份触发**：现在只给命令与文档，不在后台执行 shell。要做需要一套任务队列 + 权限 + 审计，
  不能直接在请求里 `exec`
- **系统日志**：CRMEB 是错误日志文件；本仓日志走 stdout，没有落库。要做需要先定日志保留策略
- **装修 / 应用**两块仍未做：CRMEB 的「装修」是页面 DIY，「应用」是插件市场；
  对应到本仓是「首页模块编排」与「支付/通知/存储的接入清单」，各是一独立阶段
