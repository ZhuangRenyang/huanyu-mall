# ADR-078：按 CRMEB 标准版做全功能对齐（撤销 ADR-014 的营销排除）

- 日期：2026-11-14
- 状态：已采纳（取代 ADR-014 中「不做秒杀/拼团/分销/积分/直播」的条款）
- 关联：ADR-077（原地重建）、`docs/02-architecture/crmeb-alignment.md`

## 背景

ADR-014 当初的取舍是「营销玩法保持克制」，只做交易骨架。
用户现在明确要求「CRMEB 全功能都要包括」，产品目标从「够用的自营商城」
改为「功能面对齐 CRMEB」。

## 决策

### 1. 范围：CRMEB 标准版（单商户 B2C）

包含 138 项后台菜单对应的能力；**不包含** B2B2C 多商户与 O2O 多门店
（那是 CRMEB 另外两条产品线，数据模型与权限体系完全不同，另立项目）。

### 2. 分九期，每期独立交付

A 信息架构（本次完成）→ B 装修全量 → C 应用 → D 营销（拼团/砍价/秒杀/积分/分销/直播）
→ E 会员（等级/分组/标签/充值/余额/会员卡）→ F 内容 CMS → G 财务统计
→ H 店面移动端/小程序 → I AI（LangChain.js）。

每期独立提交、独立验收、独立回滚；不合并成一次大爆炸。

### 3. 资损防护不因「对齐功能」而降级

秒杀、拼团、分销、余额充值都属于「会真金白银出错」的功能，必须：

- 库存扣减走同一条原子条件 UPDATE（现有 `allocateAndReserve`），不做「先查再减」；
- 活动有预算上限与自动止损（超卖/超发即停，不做无人值守补偿打款）；
- 退款仍然只有 `POST /admin/refund-requests/:id/approve` 一个人工入口（ADR-023 不变）；
- 分销层级与佣金比例受合规上限约束，佣金结算进独立流水，不直接改订单金额；
- 所有金额服务端计算（铁律 13 不变）。

### 4. 与 ADR-014 的关系

ADR-014 的「简单优先」作为**工程约束**继续有效（不过度抽象、不引入无必要依赖）；
其「不做哪些营销功能」的**产品取舍**由本 ADR 取代。

## 后果

- 后台导航拆为九组：首页/商品/订单/客户/营销/装修/应用/设置/维护
- 装修与应用独立成页；设置只保留「店铺怎么卖」
- 后续八期按清单推进，每期一份 ADR 记录数据模型与资损防护

## 遗留

- 直播带货依赖微信资质与推流服务，属外部依赖，排在最后一期
- 电子发票需要税务服务商接入，先做手工发票登记
- 全量功能意味着更大的攻击面：C 期起每个写接口都要过权限与审计，D 期起加活动级限流
