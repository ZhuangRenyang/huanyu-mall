# ADR-043：营销三张列表的筛选、搜索与分页

- 日期：2026-11-12
- 状态：已采纳
- 关联：ADR-031（后台订单列表同款问题）、ADR-037（商品列表分页）

## 背景

后台的促销、优惠券、礼品卡三个列表，数据层都是 `listX({ limit: 100 })`，然后整表渲染，没有分页也没有搜索。

更严重的是促销列表的筛选：

```ts
if (q.type || q.status) {
  // repo 暂不支持按 type/status 过滤（硬约束不改模块），此处拉全量后内存过滤 + 分页。
  const all = await listPromotions({ limit: MAX_PAGE_OFFSET, offset: 0 });
  const filtered = all.items.filter(...);
  items = filtered.slice(q.offset, q.offset + q.limit);
}
```

这是 ADR-031（后台订单列表）逐字重演的坑：**先拉固定条数，再在内存里筛**。超过 `MAX_PAGE_OFFSET` 的活动永远不会出现在任何一页里，而且 count 也来自内存过滤结果——商家看到「共 3 条」以为活动被人删了。

优惠券和礼品卡同理：`limit: 100` 之后没有下一页，第 101 张券不存在。

## 决策

### 1. 筛选与搜索下沉到 SQL

- `ListQuery` 增加 `q?: string`；促销另有 `PromotionListQuery { type?, status? }`
- 促销：`name ILIKE %q% OR code ILIKE %q%`（商家手里可能只有一个活动码）
- 优惠券：`name ILIKE %q%`（券码在另一张表，按码搜需要 join，V1 不做）
- 礼品卡：`code ILIKE %q%`（商家拿到的是卡号，不是「哪张卡」）
- 路由层删掉 `MAX_PAGE_OFFSET + 内存过滤` 分支；`count` 一律来自 SQL 的 `count(*)`

### 2. 三张列表统一「搜索框 + 总数 + 上下页」

抽了两个小组件 `ListSearch` / `ListPager`（`apps/admin/src/components/list-toolbar.tsx`）。抽出来不是为省几行 JSX，而是让三张表的分页行为一致：

- 搜索框 300ms 防抖，换关键字回第一页（停在第 3 页搜一个只有 1 条的关键字会看到空列表）
- 总数用服务端口径，不是当前页条数
- 加载中禁用翻页按钮，避免连点发出跨页请求

### 3. 一页 20 条

与后台订单列表一致。营销数据量通常小于订单，20 条足以一屏看完；再大就靠搜索，而不是靠翻页。

### 4. 不做的事

- **不按券码搜索**：要 join `voucher_code` 并去重，属独立需求（「这张码属于哪张券」更适合做一个码查询页）
- **不做排序切换**：列表默认按创建时间倒序，商家找东西靠搜索；营销列表不是分析报表
- **不做批量操作**（批量停用/删除）：营销活动是低频高影响操作，批量停用一次能废掉一整场活动

## 后果

- promotion 模块：`ListQuery` / `PromotionListQuery`、三个 `list*` 的 SQL 条件
- API：三个列表端点接 `q`（促销另有 `type`/`status`），`listSearchQuery` 统一形状
- 后台：三张列表加分页与搜索，`admin-promotions.ts` 的三个 `list*` 返回 `{ items, total, hasMore }`
- mock 模式同步实现本地筛选与切页：只做 live 分支的话，演示与线上会是两种行为
- 测试：`admin-promotions-list.spec.ts` 5 条（名称搜索命中/未命中、type 筛选、券名搜索、卡号搜索、分页与 count 独立）

## 遗留

- 券码反查券的页面未做（见「不做的事」）
