# ADR-031 后台订单列表：筛选、搜索与分页都在服务端

- 日期：2026-11-12
- 状态：Accepted
- 范围：order 模块（多状态筛选、关键字搜索）、API（`admin/orders` 查询参数）、admin（订单页页签 + 分页）
- 关联：ADR-030（工作台「去发货」指向这个列表）、ADR-022（商品列表已改成服务端分页，同一套做法）

## 背景

订单页的筛选与搜索是**前端本地**做的：`listOrders()` 一次拉 100 条，再在浏览器里过。

两个问题：

1. **静默漏单**：第 101 单之后的订单永远不会出现在「待发货」页签里，商家不知道；
2. **和工作台对不上**：工作台显示「待发货 5」，点进去可能是空列表 ——
   那 5 单不在前 100 条里。

商品列表在 ADR-022 已经改成「服务端分页 + 服务端筛选」，订单列表没跟上。

## 决策

### 1. 页签 = 一组订单状态，由服务端筛

| 页签 | 状态集合 |
|---|---|
| 全部 | 不过滤 |
| 待发货 | `paid` |
| 部分发货 | `partially_fulfilled` |
| 已发货 | `fulfilled` / `delivered` |
| 退款中 | `refund_pending` |
| 已退款 | `refunded` |

**「待发货」只含 `paid`**：`refund_pending` 是另一个状态，混进来会出现
「货发了、钱也退了」——这是真金白银的错误，不是排版问题。

API 用逗号分隔多状态：`?status=paid,partially_fulfilled`。
单值仍然兼容（老调用方不会炸）。

### 2. 搜索订单号或邮箱

`ilike` 匹配 `order.id` 与 `order.email`，不做商品标题搜索 ——
订单号是商家手里唯一的线索（顾客报单号、客服查单）。

### 3. 列表返回行项

`listOrders` 返回的 `OrderDTO` 不含行项，列表的「商品」列在 live 模式下是一列空白。
改用 `listOrderSummaries`（一次批量取行项），复用已有 `mapOrder` 映射，
列表与店面的「我的订单」字段口径一致。

### 4. 角标复用 `countByStatus`

页签上的数字来自一次 `GROUP BY status`，前端按页签的状态集合求和。
不在前端数当前页的条数 —— 那是「这一页有几条」，不是「一共有多少单」。

## 后果

- 商家点「待发货 5」看到的就是那 5 单，翻页也不会漏。
- 列表有加载态、空态、错误态与分页控件（上一页 / 下一页 + 总数）。
- 工作台「去发货」跳转带 `?filter=unfulfilled`，落地即是待发货页签。

## 不做

- **不做按时间范围筛选**：淘宝有「近 3 个月」这类筛选，但没有店家反馈的需要；
  真要做，加一个 `since` 参数即可，不必现在铺开。
- **不做多条件组合（状态 + 金额 + 商品）**：先把最常用的「状态 + 单号」做扎实。
- **不做服务端导出**：导出是另一个量级（大文件、异步任务），单独排期。
