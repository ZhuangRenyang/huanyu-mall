# ADR-051：退货退款（货没回来不打款）

- 日期：2026-11-13
- 状态：已采纳
- 关联：ADR-023（只做人工审核，不做自动退款）、ADR-024（退款申请单与资金流水分开）

## 背景

售后只有一种处理方式：商家点「同意」→ `refundOrderWorkflow` 立刻打款 → 订单 `refunded`。

但真实场景里最常见的售后是**退货退款**——顾客已经收到货，要退回来。按现在的实现：

1. 商家同意 → 钱当场退回；
2. 顾客是否寄回、寄到哪、寄没寄，系统一无所知；
3. 商家净亏一单，而且这笔亏损是由「同意退款」这个正确动作造成的。

淘宝把这一笔钱拆成两道闸：**同意退货**（不动钱，等买家寄回）→ **确认收货**（这时才退款）。
ADR-023 说过「不做自动退款」——这条与之同源：钱不能在货没回来时无人值守地出去。

## 决策

### 1. 新增售后类型 `resolution`，两条路各自独立

| 类型 | 适用 | 状态路径 | 打款时机 |
|---|---|---|---|
| `refund_only` | 未发货 / 已协商不退货 | `pending → approved` | 商家同意时 |
| `return_refund` | 已发货、已收货 | `pending → awaiting_return → returned → approved` | **商家确认收到货时** |

`resolution` 默认 `refund_only`：历史单据本来就是「同意即退」的语义，补默认值比让老数据落进未知分支安全；
老客户端不传这个字段时行为不变。

### 2. 未发货的订单不能申请「退货退款」

`supportsReturnRefund(status)`：只有 `partially_fulfilled / fulfilled / delivered / completed` 允许。
未发货的订单让顾客选「退货退款」，商家同意后单据进「待买家寄回」——买家手里没货可寄，永远走不出来。

### 3. 服务端守卫两条路互不串门

- `approveRefundRequest` 遇到 `return_refund` 直接抛 `refundResolutionMismatch`：**货没回来不许打款**。
- `agreeReturnRequest` 遇到 `refund_only` 同样抛错：仅退款该直接退，不该进等寄回。

只靠后台按钮文案区分是不够的——接口能直连，守卫必须在服务层。

### 4. 退货物流必须填公司与单号

`shipReturn` 要求两者都非空（路由层再限 4–60 字符），单据转 `returned` 并记 `return_shipped_at`。
没有单号，「已寄出」就是一句话；商家收到空包裹也无从对账。
买家寄件**不算商家处理**，所以 `setReturnShipment` 不碰 `reviewed_at`。

### 5. 在途唯一性扩展到三个状态

原唯一索引只约束 `status = 'pending'`。买家在「等寄回」期间再提一张，商家会退两次。
迁移只增不删（不能 DROP 旧索引），因此**再加一条** partial unique：

```sql
CREATE UNIQUE INDEX uq_refund_req_return_active
  ON refund_request (order_id) WHERE status IN ('awaiting_return', 'returned');
```

status 单值，两条 partial 索引合起来正好等价于「三种在途状态里最多一条」。
仓储侧 `findPendingRefundRequest` 相应改名为 `findActiveRefundRequest`（语义变了，名字要跟上）。

### 6. 谁能做什么

| 动作 | 谁能做 | 状态前提 |
|---|---|---|
| 同意退货 | 商家 | `pending` + `return_refund` |
| 填退货单号 | 买家（按**订单**归属校验） | `awaiting_return` |
| 确认收货并退款 | 商家 | `returned` |
| 拒绝 | 商家 | 只有 `pending` |
| 撤销 | 买家 | `pending` / `awaiting_return`（已寄回不许单方面撤） |

「已同意退货还能不能拒绝」——不能：买家可能已经把货寄出，商家此时反悔，货和钱都在路上。
想反悔只能等买家自己撤销。已寄回（`returned`）也不允许撤销，货在路上。

### 7. 界面照淘宝的位置

- **顾客**：申请时选「仅退款 / 退货退款」（未发货订单不出现后者）；同意后退货卡片变成「请寄回商品」+
  物流公司/单号两个输入；寄回后显示单号并说明「等待商家确认收货」。
- **后台**：页签加「待买家退货」「待收货」，排在待处理之后、已同意之前；
  行内显示售后类型与退货单号；`returned` 行的主操作是「确认收货并退款」；
  同意弹窗按类型分两种文案——**退货退款那版明确写「这一步不会打款」**。

## 后果

- order 模块：迁移 `0008_return_refund.sql`；`RefundResolution`、两个新状态、五个退货字段；
  `supportsReturnRefund`；服务新增 `agreeReturnRequest` / `shipReturn` / `confirmReturnReceived`
- API：`POST /store/orders/:id/refund-requests` 收 `resolution`；
  `POST /store/refund-requests/:id/return-shipment`（买家填单号）；
  `POST /admin/refund-requests/:id/receive-return`（确认收货并打款）；
  `/approve` 按类型分支
- SDK：`submitReturnShipment`、`receiveReturn`、`requestOrderRefund` 带 `resolution`
- 测试：order 模块 +10（未发货不许退货退款、缺省仅退款、同意不打款、两条路互斥、
  单号必填、确认收货才 approved、未寄回不许确认、在途唯一、寄回前可撤销）；
  api +8（申请带类型、同意不调工作流、仅退款仍打款、填单号、单号过短 400、确认收货打款、未寄回 409）

## 遗留

- **退货地址**：现在靠客服沟通，没有「店铺退货地址」字段。要做得像淘宝（同意时自动带出地址），
  需要 settings 域加收货地址，属独立工作
- **退货超时关闭**：淘宝 N 天不寄回自动关闭申请。与「不做无人值守状态变更」冲突，
  本仓明确不做
- **部分退货 / 换货**：一期只全额退，换货是另一条链（补发 + 差价），不在本期
- **退货入库**：确认收货后不自动回补库存（货可能已损坏）。要回补需人工在库存页调整
