# ADR-075：取消订单必须释放库存，并让顾客能取消未付款订单

- 日期：2026-11-13
- 状态：已采纳
- 关联：ADR-013（预留与分配）、ADR-023（不做自动退款）、ADR-051（退货退款）

## 背景

两件事，一个根因和一个缺口。

### 1. 后台取消订单没有释放预留（库存泄漏）

`POST /admin/orders/:id/cancel` 当时只调了 `order.cancelOrder(id)` —— 改状态，
**没有碰库存**。下单时 `allocateAndReserve` 把货从 `available` 挪到了 `reserved`，
这笔预留一直挂在 `reserved` 上：

- 商品页显示「有货 3 件」，但那 3 件其实是某张已取消订单占着的；
- 顾客下单时分配不到货，看到「库存不足」，商家在后台看库存又是有的。

这不是显示问题，是**货卖不出去**。仓库里其实有货，系统认为没有。

`orderCancelWorkflow` 早就写好了（取消 + 释放预留两步），但**没有任何地方调用它**——
定义了没用，等于没写。

### 2. 顾客不能自己取消未付款订单

淘宝「待付款」订单有「取消订单」。我们后台能取消，顾客只能等，或者干脆不管
（未付款订单一直占着库存）。这既不符合顾客预期，也让库存被无效订单占住。

## 决策

### 1. 取消 = 状态 + 释放预留，两件事一起做

新增 `cancelOrderAndReleaseStock(deps, orderId)`（`apps/api/src/lib/cancel-order.ts`），
后台与店面共用：

1. 查该单的全部预留，只挑 `status = reserved` 的；
2. 跑 `orderCancelWorkflow`（第一步取消订单、第二步释放预留）；
3. 工作流返回后再调一次 `cancelOrder` —— 对已取消是幂等空操作。

第 2 步的顺序（先取消、后释放）是有意的：反过来先放货、取消失败，
就会出现「货已放回、单还挂着」，那张单还能继续付款，等于超卖。
状态先落终态，最坏情况是「单已取消、货还没放回」—— 这种可由重试修好，不会卖超。

第 3 步不是冗余：步骤顺序里状态在前，但如果释放步骤抛错、整次工作流失败，
事务外重试需要一个「已经是终态也不报错」的入口。`cancelOrder` 正好是幂等的。

### 2. 释放必须幂等

新增 `releaseReservationIfReserved(id)`：不存在 / 已释放 / 已提交都直接返回。

原来的 `releaseReservation` 在 `status !== reserved` 时抛错。取消一张单有多条预留，
工作流重试时前几条可能已经放过了 —— 用非幂等版本会在第一条上抛错，**整次重试永远失败**，
库存就永远卡在那里。`orderCancelWorkflow` 的释放步骤改用幂等版本。

### 3. 顾客只能取消未付款订单

`POST /store/orders/:id/cancel`：

- 必须登录，且是本人订单（复用 `assertOrderAccess`）；
- 只允许 `pending` / `awaiting_payment`；
- 已付款返回 400，提示「已付款请申请售后」。

理由：取消订单**只释放库存、不涉及资金**。允许取消已付款订单就等于开了一条
绕过退款审核的路 —— 与 ADR-023「退款只有一个人工入口」直接冲突。

### 4. 界面放在订单列表，不用先进详情

淘宝的「取消订单」就在「待付款」那一单的右下角。这里同样：
`canCancel = status === 'awaiting_payment'`，点击先 `confirm`（释放库存不可逆），
成功后刷新列表。

## 后果

- inventory：`releaseReservationIfReserved`、`listReservationsByOrder` 暴露到服务契约
- workflows：`order-cancel` 的释放步骤改用幂等端口
- API：`apps/api/src/lib/cancel-order.ts`；后台取消改走它；
  新增 `POST /store/orders/:id/cancel`
- SDK：`cancelOrder(id)`；店面：`cancelUnpaidOrder` + 列表「取消订单」按钮
- 测试：api +5（释放只挑在占用的、已付款拒绝、重复取消、未登录、后台取消也释放）
- 无迁移

## 遗留

- **未付款超时自动取消**：淘宝 30 分钟未付款自动关单。这会引入一个后台定时任务，
  且属于「无人值守的状态变更」—— 不涉及钱，但仍要单独评估（任务重复执行、时钟漂移、
  与支付回调的竞态）。本轮不做
- **已付款订单的商家取消**：现在商家只能走退款审核（正确）。若将来要做「商家主动取消并退款」，
  也必须复用同一条审核链路，不能加第二个打款入口
- **取消原因**：淘宝会收集「不想要了 / 信息填错 / 重复下单」。现在不收集，
  只做状态变更；要做应落在订单状态历史里，不新增表
