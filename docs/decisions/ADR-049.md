# ADR-049：顾客确认收货

- 日期：2026-11-13
- 状态：已采纳
- 关联：ADR-036（订单页签）、ADR-042（评价）、ADR-033（物流单号）

## 背景

订单页签里有「待收货」和「已完成」，但**没有任何入口能把订单推到已完成**：

- 状态机 `fulfilled → delivered → completed`，中间必须经过 `delivered`
- `delivered` 应由承运商签收回调写入，系统里没有对接快递 API
- 结果：所有订单停在 `fulfilled`（已发货）；「已完成」页签永远是空的；评价只能靠 `fulfilled` 兜着（ADR-042 的 `REVIEWABLE_STATUSES` 里就含它）

淘宝的流程是：商家发货 → 顾客收到后点「确认收货」（或超时自动确认）→ 交易成功 → 可以评价。我们缺的就是顾客那一下。

## 决策

### 1. 状态机加一条边：`fulfilled → completed`

`delivered` 的语义是「承运商确认签收」，不是顾客动作。顾客主动确认收货时，跳过它是正确的：

- 有物流回调的店：`fulfilled → delivered → completed`，顾客点确认时订单可能已在 `delivered`，那条边本来就有
- 没有物流回调的店（绝大多数自建站）：`fulfilled → completed` 直达

不加这条边，顾客点「确认收货」会撞上状态机报错，而商家没有任何办法补救。

### 2. 只有买家本人能确认

- `assertOrderAccess`：订单有 `customer_id` 时必须本人（游客单号查询只能看，不能操作）
- 商家后台**不提供**「代确认收货」：替顾客承认「货收到了」，会让「未收到货」的纠纷失去凭据

### 3. 只接受 `fulfilled` / `delivered`

`paid`（未发货）点了没有意义；`completed` 重复点由状态机幂等返回。前端只在「待收货」显示按钮，服务端再守一次。

### 4. 前端：时间线下面一块，带二次确认

- 位置：订单时间线之后、商品明细之前——顾客点进详情最想知道「这单现在要我做什么」
- `window.confirm` 二次确认：确认收货不可撤销（撤销要商家走退款流程）
- 成功后让父组件重拉订单：状态徽标、时间线、「已完成」状态、评价入口一起更新
- 演示模式（mock）把状态写进 `sessionStorage` 覆盖表：示例订单是常量，否则刷新就回到「待收货」，「确认 → 评价」这条链在演示里走不完

### 5. 不做的事

- **超时自动确认收货**：淘宝是 10 天自动确认（平台担保交易）。自建商城没有平台兜底，自动把订单判成「已完成」会让顾客在没收到货时失去退款凭据。这条与「不做自动退款」同一条原则：钱和交易状态都不能无人值守地变
- **确认收货后自动打款给商家**：支付已在线下/渠道侧完成，系统不做资金托管
- **确认收货触发评价提醒**：需要通知模板与延迟任务，属通知域独立工作

## 后果

- order 模块：状态机 `fulfilled` 出边增加 `completed`；单测覆盖「可直达、不能跨级、不能回退」
- API：`POST /store/orders/:id/confirm-receipt`（200 返回整单；400 状态不符；403 非本人）
- 店面：`confirmReceipt()`（live 走接口，mock 写覆盖表）、订单详情的确认区块、父组件重拉
- 测试：order 模块 +1、api +4（401、未发货 400、待收货 200、他人订单 403）

## 遗留

- 「已完成」页签现在有数据了，但没有「交易完成时间」字段可展示：需要 `completed_at` 或从 status history 取，属订单时间线的独立改进
- 物流轨迹仍未对接（`delivered` 仍无人写入）：需要快递公司 API 与回调验签
