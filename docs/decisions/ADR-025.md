# ADR-025 顾客注册方式：邮箱注册与手机号注册二选一

- 日期：2026-11-12
- 状态：Accepted
- 范围：auth 模块（设置表、验证码双通道、注册流程）、customer 迁移、API（`store/auth`、
  `admin/settings/auth`）、admin 设置页、storefront 认证表单、notification（通用发信端口）
- 关联：ADR-024（顾客账号真实化）、ADR-016（通知走 outbox）

## 背景

ADR-024 把顾客侧接上真实后端后，注册只剩一条路：`email + password`，没有任何验证。
用户提了四条要求：

1. 支持邮箱注册与手机号注册二选一，两者都要验证；
2. 注册必须填写手机号；
3. 验证码可通过邮箱验证，也可通过手机号验证；
4. 后台系统设置里可切换「邮箱注册」还是「手机号注册」。

改造前的实际状态：

| 位置 | 问题 |
|---|---|
| `AuthService.register` | 只收 email + password，无验证码、无手机号，`emailAlreadyRegistered` 一查就能枚举 |
| `sendVerificationCode` | 只允许 `channel === "sms"`，邮箱通道直接 `invalidVerificationCode()` 硬拒 |
| `auth_settings` | 不存在，注册方式是代码里的常量 |
| 店面 AuthForm | 注册写成「邮箱 + 密码 + 手机号（选填）」，手机号填了也没验证 |

邮箱注册拿到一个没验证过的邮箱，等于账号主体是假的：找回密码、通知、售后联系全都落空。

## 决策

### 1. 注册方式做成店铺设置，二选一

`auth_settings.register_mode`（单行表 `auth_default`）：

| 值 | 语义 | 参照 |
|---|---|---|
| `email`（默认） | 邮箱 + 密码注册，手机号必填并验证 | Shopify |
| `phone` | 手机号 + 验证码，注册即登录 | 淘宝 |

- **单一事实来源**：后台 `PUT /admin/settings/auth` 写入，店面 `GET /store/auth/settings` 读，
  前端不硬编码。店面读不到时按 `email` 渲染（独立站默认），不因为后台没响应就把注册藏起来。
- **服务端守，界面只是体验**：
  - `mode = phone` 时 `POST /store/auth/register` 直接拒（`registerModeDisabled`）；
  - `mode = email` 时，陌生手机号**不能**用验证码自动注册 —— 否则 `loginWithPhoneCode`
    就变成绕过注册方式的后门。已存在的身份不受限（两种模式都能用手机号 + 验证码登录，
    顾客不该因为当初填了哪个字段被锁在门外）。

### 2. 邮箱注册：邮箱 + 密码 + 手机号（必填）+ 验证码，验证码双通道

- **手机号必填**：它是这个账号的第二条登录入口（手机号 + 验证码），也是国内顾客最习惯的那条。
  只存不验的选填手机号没有意义 —— 从来没有验证过的号码不能当登录主体。
- **验证码双通道**（`channel: "email" | "sms"`）：海外顾客可能收不到国内短信，国内顾客可能
  不常用邮箱。让顾客选哪条通道能收到，比替他猜一条更省事。
- **顺序：先查重，再验码**。邮箱/手机号被占时不必消耗顾客的验证码；反过来「先验码再查重」
  会让被占用的号码白白烧掉一次机会。
- 注册成功后 `identity` 同时写 `email` 与 `phone`（`phone_verified_at` 即写入时刻）。

### 3. 手机号注册 = 注册即登录，不设独立注册表单

淘宝做法：第一次输验证码就是注册，之后每次输码就是登录。
`mode = phone` 时店面**不显示「注册」页签** —— 让顾客先判断「我是新用户还是老用户」
是多余的一步，而且大部分人判断错。

### 4. 邮件通道复用通知模块的 SMTP

- `INotificationModuleService.sendMail()`：通用发信，**不落 `notification` 表** ——
  验证码 5 分钟就作废，进派发表只是噪声。
- `apps/api/src/infra/email-transport.ts`：生产未配 SMTP → 明确报错；开发 → 打日志
  （配合 `AUTH_EXPOSE_DEV_CODE`，前端直接显示验证码自测）。
- 与 `sms-transport.ts` 同一原则：**宁可不发，也不假发**。商家以为发出去了、顾客永远收不到，
  比直接报错更糟。

### 5. 布局：设置 → 顾客账号（不是「系统」）

按 MEMORY 的布局规则判断：这个配置决定「店铺怎么接待顾客」，不决定「系统怎么跑」。
所以它和「税务」同级，放在设置页的 tab 列表里，不塞进「系统」。

只做二选一，**不做「两种都开」**：邮箱注册要密码 + 手机号 + 验证码，手机号注册只要
手机号 + 验证码，两个表单字段完全不同；同时开会让注册页变成四不像。

## 数据库变更

| 文件 | 内容 |
|---|---|
| `auth/migrations/0003_settings.sql` | `auth_settings` 单行表（`register_mode`），种子行 `auth_default` |
| `auth/migrations/0002_phone_login.sql`（前序） | `auth_identity.email` 可空、`phone` 唯一索引、`verification_code` 表 |
| `customer/migrations/0002_phone_signup.sql`（前序） | `customer.email` 可空、`phone` 索引 |

## 后果

- 注册多一步（验证码），换来的是**手机号真实可收信**：后续短信通知、售后联系、验证码登录都站得住。
- 商家必须配一个通道才能注册：短信要 `SMS_PROVIDER`，邮件要「设置 → 通知」里的 SMTP。
  都没配时发码接口明确报「通道未配置」——这是有意为之，不做静默降级。
- 开发环境：未配 SMTP 也能走通邮箱验证码（日志 + `dev_code` 回显），不影响自测。
- 测试：`InMemoryAuthRepository` 增加设置与 `rewindCodeCooldown`；新增 17 条 auth 模块用例
  与 9 条 API 契约用例（公开读、RBAC、审计、入参校验）。

## 不做

- **不做「两种注册都开放」的开关组合**：字段冲突，页面会变成四不像。
- **不做邮箱验证码登录**：登录仍走「密码」或「手机号 + 验证码」。邮箱验证码只用于注册，
  多加一条登录路径只是多一个被刷的入口。
- **不做自动注册兜底（email 模式下）**：手机号验证码自动建号会让注册方式开关形同虚设。
- **不做找回密码**：等短信/邮件通道在生产跑顺了再单独做，避免一次改三处凭证流程。
