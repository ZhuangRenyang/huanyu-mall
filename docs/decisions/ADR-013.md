# ADR-013 多仓履约深化（K1）：优先单仓、不够才拆 + 原子预留 + 仓间调拨

- 日期：2026-11-11
- 状态：Accepted（用户 2026-11-11 决策：多仓先行 / **优先单仓，不够才拆** / 做基础调拨。
  同日经历两次调整：先「允许跨仓拆单」→ 再「单仓满足（要简单）」→ 最终「优先单仓、不够才拆」。
  最终理由：日常订单不该拆包裹，但两仓各一半、凑起来够的订单也不该直接拒掉。）
- 范围：二期第 2 项（多仓部分）。税务深化（K3）另立 ADR，不与本项混做。

## 背景

一期按 PRD K1 砍单：**保留 `stock_location` / `inventory_level`（仓 × SKU）/ `reservation_item`（带 `stock_location_id`）三个维度，只启用 1 个默认仓**。当时的硬约束是「reservation 绝不可简化成下单即扣库存」——这一条守住了，所以本次不需要改表结构就能接多仓。

当前阻断点（已核实）：

1. `apps/api/src/routes/store/checkout.ts:30` 取 `locations[0]`，所有行项都从第一个仓预留——**多仓等于没接**。
2. `packages/modules/inventory/src/services/inventory.service.ts:66` 的 `reserve()` 是 **check-then-act 无锁**：先 `findLevel` 读可用量、判断、再 `updateLevel` 写绝对值。并发下两单都能通过检查，后写覆盖先写 → **超卖**。一期的量级掩盖了它，多仓一开就是资损。
3. `fulfillment` 表**没有仓库字段**，无法按仓拆发货单。

## 决策

### 1. 分配策略：优先单仓，不够才拆（两段式）

- 仓按 `stock_location.priority` **降序**（**大者优先**，与既有 `listLocations()` 的 `ORDER BY priority DESC` 一致）；同优先级按仓库创建顺序，**老仓优先**。
- **第一段**：挑第一个能一次性满足整单所有 SKU 的仓。命中时一单只产生 1 条预留、1 张发货单——绝大多数订单走这条路径。
- **第二段**：没有单仓能整单满足时，退化为按优先级贪心拆分，从多个仓凑；此时产生多条预留、多张发货单。
- **两段都失败**（各仓合计仍不足）→ 整单失败，`available` 返回各仓合计。
- 取舍：纯单仓会拒掉「两仓各一半、合起来够」的订单；纯拆单会让日常订单频繁变多包裹。两段式兼顾。

### 2. 分配与预留必须在一个事务里，且用行锁

新增 `allocateAndReserve(orderId, items)`，单事务内完成：

```
1) 取「变体 → 库存项 → 各仓可用量」快照
2) 纯函数 planAllocation 挑出唯一能满足整单的仓（可单测）
3) 条件 UPDATE 占用（WHERE available >= qty），写 1 条 reservation_item
```

条件与增量写在同一条 SQL 里（`available_quantity >= qty` 进 WHERE），不做「先查后写」。

**禁止**再出现「先读可用量、再写绝对值」的写法：并发下会丢更新。锁的是 `inventory_level` 行，粒度 = 仓 × SKU。

**幂等**：同一 `orderId` 重复调用返回已有预留，不重复扣减（workflow 重放安全）。

### 3. 履约：一单一仓 / 拆分时按仓分别发

- `fulfillment` 增加 `stock_location_id`（可空，历史数据为 null 不阻塞）。
- **一张发货单只对应一个仓**。
- 单仓命中的订单：创建发货单**不需要选仓**，后端取唯一预留仓；后台只填「承运商 + 运单号」。
- 拆分兜底的订单：新增 `GET /admin/orders/:id/fulfillment-plan`，按「预留 + variant → 订单行」映射，
  由后端算出**每个仓要发哪些行、各几件**；后台按计划逐仓展示，操作员只填该仓运单号，
  不再选仓、不再手工分行填数量。
- 预留映射不到订单行时计入 `unmatched_quantity` 暴露出来，不静默丢数量。
- 未指定仓库且预留跨仓、又没走发货计划时仍明确拒绝（`stockLocationRequired`）。
- 发货数量必须等于该仓预留数量：一期不支持部分发货。这条同时修掉一个既有缺陷——原 `createFulfillment` 不管 items 传什么都会关联订单**全部**预留，部分发货会把整单库存扣掉。

### 4. 仓间调拨：独立流水，不动预留

新增 `inventory_transfer` 表：`from_location_id` / `to_location_id` / `inventory_item_id` / `quantity` / `status`（`pending` | `completed` | `cancelled`）/ `note` / `created_by`。

- 完成调拨：源仓 `stocked -= qty`、目标仓 `stocked += qty`，`reserved` **不变**（预留跟着订单走，不跟着货走）。
- 校验：源仓 `stocked - reserved >= qty`，否则拒绝（不能把已承诺给订单的货调走）。
- 不做在途库存（`pending` 只是登记，不占量）；跨仓在途模型留到需要时再评估。

### 5. 可用量的展示口径

- **店面聚合**：`getAvailability` 不传 `locationIds` 时返回所有仓之和（现状已如此），避免暴露内部仓结构。
- **后台按仓**：库存页展示「仓 × SKU」的 `stocked / reserved / available`，调拨入口在同一页。
- 下单时的仓选择**只由后端决定**，客户端不传仓库（铁律 13）。

## 后果

**收益**：日常订单不拆包裹；主仓缺货时优先整单换仓，实在凑不齐才拆，不丢单；库存账在并发下正确；运营可调拨补货。

**代价与风险**：

- 拆分只在「没有任何单仓能整单满足」时发生，但仍然存在：一旦拆单，后台要多发一次货、顾客可能收到多个包裹。
- 结账链路多了一次分配计算与条件 UPDATE → 热点 SKU 上会串行。单商户量级可接受。
- 运费口径：拆分订单仍按订单收一次运费，多包裹成本由商家承担（OPEN-DECISIONS）。
- 历史发货单 `stock_location_id` 为 null，报表按仓统计时需把 null 归入"未标记"。

## 不做（本项明确排除）

- 在途库存 / 调拨单审批流 / 仓间自动补货建议
- 按仓库的运费方案与配送时效（属 K2 承运商 + 运费深化）
- 仓容量、货位（bin）级管理
- 税务深化（K3）：另立 ADR，避免两项混做导致账目问题无法归因

## 验收口径

1. **优先单仓**：主仓 1 件、备用仓 2 件，下单 2 件 → 1 条预留，整单落在备用仓；一张发货单即可发出。
2. **拆分兜底**：两仓各 2 件、下单 3 件 → 2 条预留（2+1）、2 张发货单，两仓各自出库。
3. **合计不足**：两仓各 2 件、下单 5 件 → 拒单，两仓库存都不动。
4. 并发预留：同 SKU 库存 10，10 个并发请求各要 3 → **只有 3 个成功**，`reserved` 恰好 9，无负数、无超卖。
5. 调拨：A 仓 20 → B 仓 5 后，A=15/B=+5，源仓可用量不足时拒绝。
6. 幂等：同一订单重放预留不重复扣减。
7. 全部金额与数量为整数，无浮点。
