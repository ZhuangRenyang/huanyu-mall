# ADR-067：商品销量「已售 N 件」

- 日期：2026-11-13
- 状态：已采纳
- 关联：ADR-041（售罄展示）、ADR-067（社交证明）

## 背景

商品卡与商品页一直只有价格，没有「销量」。淘宝几乎每个商品都带月销/已售 ——
这是转化链上最便宜的社交证明：看到「已售 1280 件」，顾客对商品的顾虑会先降一半。

我们没有这个数，不是漏了展示，是压根没算过。

## 决策

### 1. 销量按「已成交订单行」实时聚合，不另存计数器

`order.countSoldByVariantIds(variantIds)`：`order_line_item ⟕ order` 一条 GROUP BY，
`variant_id` 分组，只数订单状态属于「已成交」那几档的行数量之和。

**口径（哪些算成交）**：`paid / partially_fulfilled / fulfilled / delivered / completed`。
未付款、已取消、退款中、已退款**都不算**。

为什么不另存 `sold_count` 计数器、在下单时自增：

- 计数器要处理退款回减、取消回减、拆单、超卖，任何一条漏了就是脏数；
- 而「从订单行聚合」**永远是对的**：订单就是事实源，退款单状态一变，销量自动跟着变。

代价是每次列表/详情多一次 GROUP BY，单店订单量下可接受（已按 variant_id 建索引在 order_line_item 上）。

### 2. 接口层批量取，不做 N+1

商品列表/详情把整页的 variantId 攒起来，一次 `countSoldByVariants` 取全，
与库存、价格的既有做法一致（同一批 `Promise.all`）。

### 3. 商品级销量 = 各变体销量之和

列表的 `sold_count` 是商品所有变体的销量之和；详情同时给商品级与每变体级。
多规格商品顾客在详情页切规格时，销量跟着切到该规格（淘宝同做法）。

### 4. 只在 > 0 时显示，不给新店挂「已售 0 件」

0 件不是社交证明，是「没人买过」的负信号。`(soldCount ?? 0) > 0` 才渲染。

## 后果

- order：`countSoldByVariantIds`（仓储，join + GROUP BY + `SOLD_STATUSES` 常量）、
  `countSoldByVariants`（服务）
- API：`GET /store/products` 与 `GET /store/products/:handle` 附 `sold_count`
  （列表商品级、详情商品级 + 每变体级）
- 店面：商品卡与商品购买区显示「已售 N 件」（>0 才显示）；mock 目录补两处销量样例
- 测试：api +3（列表带 sold_count 默认 0、详情商品级与变体级、无销量变体为 0 不 undefined）
- 无迁移（聚合查询，不改表）

## 遗留

- **月销 vs 累计**：淘宝区分「月销」（近 30 天）与「累计已售」。当前给的是累计，
  月销要按 `placed_at` 加时间窗，属下一步
- **销量排序**：列表「按销量排」是常见诉求，把聚合值当排序键需要下推到 SQL
  （跨模块 join 或物化），另议
- **聚合查询性能**：真到十万订单级，GROUP BY 会变慢，届时物化 `sold_count` 或加缓存
