# ADR-009: 迁移 = drizzle-kit generate（仅 diff 提示）+ SQL 入库 + CI lint 强制「禁止破坏性迁移」

## Status: Accepted (2026-11-08)

## Background

铁律 10（数据安全）+ 简报第八节（部署升级硬性要求）：表结构全程版本化迁移，禁止手工改表；迁移只允许加表、加列等向前兼容增量变更；代码评审中出现手工改表或破坏性迁移（删表、删列、改类型）直接打回。这是"二期一键升级不伤数据"的前提。

候选：Atlas（专业迁移工具，自动 diff + lint 破坏性变更）、drizzle-kit（本项目 ORM 自带）、自研 SQL 版本化 + 手写检查。

## Decision

采用「**drizzle-kit 只当 diff 提示器 + 人工审阅 + SQL 入库 + 自研 CI lint**」：

1. 迁移文件是**纯 SQL**（`packages/modules/*/migrations/NNNN_*.sql`），是唯一事实来源；应用逻辑靠 `schema_migrations` 表保证只跑一次。
2. `drizzle-kit generate` 只用来**生成候选 SQL**，工程师审阅后手工定稿入库；**禁用 `drizzle-kit push`**（它会直接改库，绕过评审）。
3. **自研 `scripts/lint-migrations.ts` 门禁**：用 `pg-query-emscripten`（libpg_query 的 WASM 版）解析每条 SQL 的 AST，扫描并拦截以下 token：
   - `DROP TABLE` / `DROP COLUMN` / `DROP CONSTRAINT`
   - `ALTER TABLE ... ALTER COLUMN ... TYPE`（改类型）
   - `ALTER TABLE ... DROP`
   - `DELETE` / `TRUNCATE` / `UPDATE`（迁移里不允许 DML 之外的数据改写，除非显式白名单标记 `-- data-migration`）
   - `CREATE TABLE` 之外的 `RENAME`（改表/改列名需 expand-contract 两阶段）
   违反即 CI 红，合并被阻断。
4. **expand-contract 两阶段**（二期才允许第二阶段）：
   - 阶段一（expand，可回滚）：加新列（nullable 或带默认值）→ 双写 → 回填。
   - 阶段二（contract，需人工审批）：确认旧列零读取后，另开一条迁移删除——**一期一律禁止阶段二**。
5. 每次迁移执行前自动 `pg_dump` 基线备份（install.sh 第 7 步已内置），失败即停，不留半迁移状态。

## Consequences

正面：
- 破坏性迁移在合并阶段就被机器拦下，不靠人眼。
- 纯 SQL 迁移可评审、可审计、可离线重放，且与 ORM 解耦（换 ORM 迁移不受影响）。
- 与 ADR-005（SQL 唯一事实来源）一致。

负面：
- 需自研 AST lint（`pg-query-emscripten` 提供解析能力，检查逻辑自写约 150 行）。
- expand-contract 的双写阶段（二期）增加开发成本，但这是"不伤数据升级"的唯一正确做法。
- `pg-query-emscripten` 是 WASM 依赖，需确认其在 Node 26 的兼容性（否则回退到正则 + 白名单关键字，能力弱但够用）。

## Alternatives

1. **Atlas**：迁移 diff + 破坏性变更 lint 是现成的、质量高，但引入独立二进制 + 其自己的迁移历史模型，与"SQL 文件入库 + 每模块独立 migrations"的组织方式冲突，且需联网拉镜像。否决。
2. **纯 drizzle-kit push + 手动纪律**：最省事但把数据库改动的正确性交给个人，违反铁律 10 的"直接打回"精神。否决。
3. **完全手写 SQL + 无 diff 提示**：可控但不方便，schema 变更时人肉比对 DDL 易漏。否决。
