# ADR-014 产品取舍：简单优先，不做营销玩法军备竞赛

- 日期：2026-11-11
- 状态：Accepted（用户明确：不抄 CRMEB 的功能了；商城要简单方便易操作；不要秒杀这种花里胡哨的活动）
- 影响范围：二期后续全部功能取舍、后台交互复杂度、三期规划

## 背景

一期与二期前两项的建设方式是「对着电商大盘的功能清单补齐」：Promotion 三件套、礼品卡、多仓、以及规划中的 CMS/装修、B2B、多市场、AI 客服。这套清单来自 CRMEB / Shopify 一类平台的竞品对标。

但本项目的真实使用者是**一个商家，卖自己的货**，不是平台方，也不是代运营服务商。竞品的功能密度服务于「平台要满足各种商家」，对单商户来说，绝大多数是：

- 日常用不到（装修编辑器、B2B 价格表、多市场）
- 用起来很贵（秒杀要压测、拼团要处理失败退款、分销要结算）
- 一旦出问题就是资损或客诉（营销规则越复杂，越难解释「为什么这单没打折」）

继续按竞品清单铺，会让「简单」这个真正的卖点消失。

## 决策

### 1. 功能准入三问（缺一不做）

任何新功能进入排期前，必须同时回答：

1. **商家每周会用吗？** 一年用两次的，不做。
2. **三步内能完成吗？** 后台点三次还找不到的，先改交互，不要加功能。
3. **不做会丢单或违规吗？** 不会的，一律延后。

### 2. 永久不做：营销玩法

| 不做 | 原因 |
|---|---|
| 秒杀 / 限时抢购 | 要扛并发、要防超卖、要处理未付款释放；单商户的流量根本用不上 |
| 拼团 / 砍价 / 分销裂变 | 涉及多用户状态机、佣金结算、退款分摊，复杂度和资损面远超收益 |
| 积分商城 / 签到 / 抽奖 | 需要独立的账户体系与库存，运营成本高，和「卖货」无关 |
| 直播 / 内容种草 | 不是商城该内置的能力 |
| 复杂满赠 / 买 X 送 Y | 赠品要占库存、要定价、要处理退款；一期已明确不做 |

已有能力足以覆盖真实促销需求：**单品/分类折扣、订单满减、优惠券、礼品卡**。

### 3. 二期范围收敛

| 项目 | 结论 |
|---|---|
| 税务深化（K3） | **保留**。合规不是花活；当前单一税率可用，税区/多税率按真实销售国家再加 |
| 订单通知（邮件） | **保留**。下单/发货通知是基础体验 |
| 后台一键升级 | **保留**。运维刚需，且是「程序与数据分离」的兑现 |
| 商品搜索 | **按需**。商品数 < 200 时 PostgreSQL 足够；不引入 Meilisearch |
| 多语言 / 翻译全量 | **暂缓**。单市场单语言，翻译是纯成本 |
| CMS / 博客 / 拖拽装修 | **不做**。一套模板 + 设计变量已能改外观；商家不该学装修器 |
| 对外 Webhook / API Key / Sales Channel | **暂缓**。没有外部系统要对接时不建 |
| 多市场 / B2B / 按 Channel 启停支付 | **暂缓**。单商户单市场；需要时再评估，不预埋复杂度 |
| AI Gateway / AI 客服 | **不做**。没有真实客服团队时，AI 客服只会制造答非所问 |
| 三期（积分/订阅/插件市场等） | **不做**。不为其预留任何抽象 |

### 4. 已有功能的「简化义务」

范围收敛之外，已建功能也要为「易操作」让路：

- **多仓**：默认单仓。只有一个仓时，后台不出现「调拨」「仓库」入口；启用第二个仓后才显示。
- **促销创建**：用预设（全场折扣 / 满减 / 指定商品或分类），**不让商家填分类 ID、变体 ID**。
- **高级项默认折叠**：predicate、allocation 这类内部概念不出现在默认界面。
- **订单发货**：单仓订单一律两步（承运商 + 运单号）；只有拆分兜底时才出现选仓。

## 后果

**收益**：功能面收窄，交付更快；后台可解释；出错面变小；「简单」成为可交付的差异点而不是口号。

**代价与风险**：

- 客户若明确要求 B2B、多市场、分销，需要单独立项评估——本 ADR 不承诺这些能力。
- 竞品对比时会「功能少」。这是有意的取舍，销售话术要能解释：少的是不需要的，留下的是每天要用的。
- 已建但使用率低的能力（如礼品卡）不删除，但不在导航里抢位置。

## 防复发

以后若有人提「竞品有这个功能」，先回到本文第 1 节的三问；三问答不上来就不排期。范围变更需更新本 ADR，不接受口头扩范围。
