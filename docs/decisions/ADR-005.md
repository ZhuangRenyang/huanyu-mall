# ADR-005: ORM 选 Drizzle（SQL-first + 迁移文件唯一事实来源）

## Status: Accepted (2026-11-08)

## Background

铁律 10：表结构全程版本化迁移，禁止手工改表，只允许加表/加列等向前兼容增量。候选：Drizzle（0.45.4）、Prisma（7.10.1/8.0.0-rc）、MikroORM（Medusa v2 实际所用）、TypeORM（重、装饰器）。

关键事实：Medusa v2.22.4 用的是 MikroORM（证据：`packages/modules/product/package.json` 的 scripts 全是 `MIKRO_ORM_CLI_CONFIG` / `medusa-mikro-orm migration:*`）。本项目不引入 medusa 依赖，ORM 自行选型，但可借鉴"每模块独立 migrations 目录"的组织方式。

## Decision

选 **Drizzle 0.45.4 + 手写/生成 SQL 迁移文件**，SQL 是唯一事实来源：

- schema 用 Drizzle 定义（获得 TS 类型 + 查询构建器 + 关系推断），但**迁移不依赖 `push`**：用 `drizzle-kit generate` 生成 SQL 后**人工审阅 + 入库**，`drizzle-kit` 只当 diff 提示器。
- 迁移文件是 `packages/modules/*/migrations/NNNN_*.sql`，纯 SQL，按模块独立、按文件名序号应用，`migrate.ts` 记录 `schema_migrations` 表保证只跑一次。
- DAL 层 `core/db` 封装 Drizzle，业务不 import `drizzle-orm`（§11.1 的 ESLint 门禁），ORM 可替换。

## Consequences

正面：
- SQL-first：迁移就是 SQL 文件，评审、审计、回滚（expand-contract 第二阶段）都直白。
- 轻量、无引擎/无二进制依赖（对比 Prisma 需要 query engine + generate 步骤），构建快，冷启动快。
- 类型安全 + 查询构建器在同一个包里，Drizzle 的 `relations()` 仅作类型层关系推断，不强制产生外键。

负面：
- Drizzle 处于 0.45 → 1.0-rc 的过渡期（`drizzle-kit` 已出 1.0.0-rc.5），迁移 SQL 生成语义可能微调——用"人工审阅 SQL + 锁版本"吸收（§0/R6）。
- 无 Prisma Studio 那样的图形化（可用 `drizzle-kit studio`，但功能弱；一期用 `psql` + 日志即可）。
- 关系推断需要手写 `relations()`，比 Prisma 显式一点。

## Alternatives

1. **Prisma 7/8**：类型与 DX 最好，但引入 query engine + generate 产物，构建链变重；且 latest tag 已是 8.0.0-rc.33（RC 阶段），与"锁稳定版 + 只加不改"的稳定性诉求冲突；`prisma migrate` 的 diff 引擎对"增量约束"不透明（它倾向生成破坏性 SQL）。否决。
2. **MikroORM**：Medusa 同款，实体驱动，但装饰器 + 反射与 ADR-001"无反射"冲突，且迁移自动 diff 同样不透明。否决。
3. **TypeORM**：生态大但重、迁移工具弱、装饰器模式老化，与轻量自研骨架不搭。否决。
