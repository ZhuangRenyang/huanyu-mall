# ADR-037 商品列表分页：第 21 件商品也必须能被看到

- 日期：2026-11-12
- 状态：Accepted
- 范围：storefront（`lib/store-data.ts`、列表页、`product-listing.tsx`）
- 关联：ADR-022（商品列表服务端筛选）、ADR-031/036（订单列表同款做法）

## 背景

店面商品列表页不传 `limit`，服务端默认返回 20 条，**前端没有任何分页控件**。

后果很直接：第 21 件商品顾客永远看不到。商品少的店发现不了，
商品一多（超过 20 件）就会变成「店里明明有货，顾客只看得到 20 件」——
而且商家在后台看得到全部，不会察觉前台少了东西。

这是「后端支持分页、前端没用」的第三个案例（前两个是后台订单列表、顾客订单列表）。
共同点：一次拉固定条数 + 前端本地处理，数据一超过阈值就静默丢。

## 决策

### 1. 分页在服务端做

`getStoreProductsPage()` 返回 `{ items, total, hasMore }`，页面按 `?page=N` 计算 offset。

不在前端切页：那等于先把全部商品拉下来再分页，商品上到几百件就是一次几 MB 的响应。

### 2. 一页 24 件

4 列 × 6 行：桌面一屏多一点，滚一下能看到下一页入口。淘宝 pc 版也是每页 24/48 这类量级。

### 3. 页码写进 URL

`/products?q=…&category=…&sort=…&page=2`。刷新、分享、从分类页返回都能回到同一页。
翻页时保留现有筛选（`gotoPage` 会带上 q/category/sort），只替换 page。

### 4. 换筛选回第一页

`applyQuery` 重建 URL 时不带 page（现有逻辑天然满足）。
否则在第 3 页筛一个只有 5 件商品的分类，会看到空列表。

### 5. 保留 `getStoreProducts()` 数组版

首页「当季主推」只要前 8 件，不需要分页信息。让它复用分页函数并取 `.items`，
避免两套取数逻辑。

## 后果

- 顾客能翻到全部商品；「共 N 件」显示的是**服务端总数**，不再是本页条数。
- 首页多一次函数调用，无额外请求。

## 不做

- **不做无限滚动**：需要滚动监听 + 游标分页，且 URL 无法表达「滚到第几屏」；
  页码制对「回到上次看到的位置」更友好。
- **不做每页条数切换**（24/48/96）：单店 SKU 量级用不上，多一个控件多一份状态。
- **不做商品总数少于 24 时的分页条**：只有一页时显示分页是噪音。
