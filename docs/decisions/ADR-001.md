# ADR-001: 自研轻量 Module Registry 作为模块框架与依赖注入

## Status: Accepted (2026-11-08)

## Background

简报锁定「Medusa 式模块化单体 + 插件机制」，铁律 1 要求每个模块自有数据模型与服务层、边界清晰。需要回答：模块如何被注册、如何在启动时按拓扑序装配、模块之间如何取得对方 service。三个候选：NestJS（自带 DI 与模块系统，但引入整套框架与装饰器）、Awilix（成熟 DI 容器）、自研极简 Registry（对齐 Medusa 的 `Module()` 注册 + container resolve）。

关键约束：铁律 2「模块间禁止数据库外键」、铁律 4「扩展不改核心」、以及「严格自研骨架、不依赖 medusa npm 包」。因此框架必须让"模块"成为一等公民，且能被 Installer 在启动时收集、排序、注入。

## Decision

自研一个极简 Module Registry，API 形态对齐 Medusa v2（`export default Module("order", { service: OrderModuleService })`，见 `packages/modules/product/src/index.ts` 的 3 行默认导出），但实现完全自研：

```ts
// packages/core/src/module/registry.ts（约 200 行）
registry.register("order", { service: OrderModuleService, migrations: [...], linkable: OrderLinkable })
registry.resolve<IOrderModuleService>("order")   // 按依赖拓扑序实例化 + 注入 cradle
```

- 容器是**编译期可见的强类型 Map**：`resolve<T>(name)` 返回类型由 `ModuleName → ServiceType` 映射推导，不靠反射。
- 依赖注入用 **cradle 注入**（构造器收一个 `cradle` 对象，含 logger / db / cache / container），不引入装饰器与反射。
- 启动顺序 = 模块依赖拓扑序（§3 的 L0→L5），用 `scripts/check-module-graph.ts` 提前算出，启动时只按序执行。
- 生命周期三钩子：`onLoad`（纯内存装配）、`onReady`（可做 DB 断言）、`onShutdown`。

## Consequences

正面：
- 零框架依赖，无装饰器/反射，树摇干净，构建快。
- 「模块」是显式的一等公民，Installer 与门禁脚本都能枚举模块清单（迁移聚合、linkable 聚合都靠它）。
- 类型安全：`resolve("order")` 编译期就知道返回 `IOrderModuleService`，杜绝字符串写错。

负面：
- 需自己实现拓扑排序、循环依赖检测、生命周期（约 200 行，可控）。
- 没有 NestJS 那样现成的拦截器/守卫生态；这些横切能力在 Fastify 层用中间件补（§7）。
- 团队若未来想换 NestJS 需重写注册层（但 service/repository 分层不变，迁移成本低）。

## Alternatives

1. **NestJS**：模块系统成熟、生态大，但引入整套框架、装饰器元数据、依赖它的 DI 语义，与"严格自研骨架"冲突，且与 Fastify 直连（我们只想要 HTTP 层）会多一层抽象。否决。
2. **Awilix**：成熟 DI 容器，但它是"容器"不是"模块框架"，模块注册/迁移聚合/linkable 仍需自己搭，引入第三方只为省 100 行容器代码，性价比低。否决。
3. **纯手写 import（无容器）**：最简单，但模块间直接 `import` 会破坏铁律 2/3 的可替换性（无法在运行时替换模块实现、无法做模块级 mock）。否决。
