# ADR-060：库存页显示「N 人等货」

- 日期：2026-11-13
- 状态：已采纳
- 关联：ADR-059（到货提醒，本条收口其遗留项之一）

## 背景

ADR-059 让顾客能在售罄商品上登记到货提醒，补货时自动发邮件。
但**商家看不到这些登记**：他不知道哪个 SKU 有 20 个人在等，哪个只是恰好缺货。

补货预算有限时，这个差别决定先补谁。看不到需求，到货提醒就只是「顾客少流失一点」，
商家这一侧完全没有收益。

## 决策

### 1. 数据挂在库存行上，不另开一个页面

商家补货时看的是「仓 × SKU」这张表。需求热度必须在同一行，
否则他要在两个页面之间来回对 SKU —— 那种设计没人用。

### 2. 两跳查到人数，都不做 N+1

库存行只有 `sku`，到货提醒按 `variant_id` 登记，中间缺一环：

1. `product.variantIdsBySkus(skus)` —— 一次 `IN` 查询，返回 sku → 变体 id；
2. `product.countPendingStockAlerts(variantIds)` —— 一次 `GROUP BY`，返回变体 → 人数。

两跳都是批量，一页 20 行只多两次查询。

### 3. 只在有人等时显示徽标

`stockAlertCount > 0` 才渲染「N 人等货」。正常有货的行挂个「0 人等货」纯属噪音。
颜色用 warning：它是「该补货了」的信号，不是错误。

### 4. 字段可选，老后端不影响新后台

`sdk.InventoryLevelRow.stock_alert_count?: number`，前端 `?? 0`。
后台和 API 允许独立发布：老后端不返回这个字段时，界面照常工作、只是不显示徽标。

### 5. 计数口径：未通知的人

`countPendingStockAlerts` 统计 `notified_at IS NULL` 的登记。
已发过「到货了」的人不该再算进需求 —— 他们已经被服务过一次。

（若他们再次登记，`notified_at` 会被清空并重新计入，与 ADR-059 的重新登记语义一致。）

## 后果

- product：`listVariantIdsBySkus`（仓储）、`variantIdsBySkus` / `countPendingStockAlerts`（服务）
- API：`GET /admin/inventory-levels` 的每行多一个 `stock_alert_count`
- SDK：`InventoryLevelRow.stock_alert_count?`
- 后台：库存表的「可用」列后挂「N 人等货」徽标（>`0` 才显示）
- 测试：api +1（库存行必然带 `stock_alert_count` 且是数字）

## 遗留

- **按需求热度排序**：现在只能看，不能按「等货人数」排。要做得把排序下推到 SQL
  （跨模块 join 或二次排序），等真有商家一天补几十个 SKU 再说
- **一键通知**：已经补货但没触发事件（比如线下手工改过库存）时，缺一个「手动补发通知」入口
