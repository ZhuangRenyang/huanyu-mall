# ADR-070：月销与累计销量分开算

- 日期：2026-11-13
- 状态：已采纳
- 关联：ADR-067（商品销量）、ADR-068（销量排序）

## 背景

ADR-067/068 只做了一个口径：**累计**成交量。商品卡与购买区写「已售 1000 件」，
排序也按这个数。

对着淘宝看，这个口径不对：

1. **淘宝商品卡写「月销」**，不是累计。三十天前的销量对今天的顾客没有参考价值 ——
   一个三年前爆过、现在没人买的商品，挂着「已售 10 万件」会误导人。
2. **淘宝「销量」排序排的是近 30 天**。按累计排的话，老爆款永远压住当季新品，
   新品没有曝光机会。

累计不是没用：详情页写「累计已售」是可信度（这个商品不是新上架的野牌子），
但它不该是卡片上的主口径。

## 决策

### 1. 一个仓储查询，两个时间窗

`countSoldByVariantIds(variantIds, opts?: { since })`：

- 不传 `since` → 累计（原来的行为，不动）；
- 传 `since` → 只数 `order.placed_at >= since` 的成交行。

`SOLD_STATUSES` 的口径不变（已付款/部分发货/已发货/已收货/已完成），
未付款、取消、退款都不算。时间比较用**下单时间**而不是付款时间 —— 淘宝月销也按下单口径。

`countSoldByVariants` 在服务层原样透传，不改写 `since`（改写就是第二套口径）。

### 2. 窗口长度是模块导出的常量

`MONTHLY_SOLD_DAYS = 30` + `monthlySoldSince(now)` 纯函数，导出自 `@mall/order`。

接口层调 `monthlySoldSince()`，不自己写 `30 * 24 * 3600 * 1000` —— 复制一份迟早漂移。
抽成接收 `now` 的纯函数是为了能测边界（29 天在内、31 天不在）。

### 3. 接口同时下发两个字段

- `sold_count`：累计，语义不变（后台与老前端不用改）；
- `monthly_sold_count`：近 30 天，新增。

列表与详情都给。列表多一次 GROUP BY 是值得的：卡片要显示月销，缺了就得逐个详情页取，
那才是 N+1。

### 4. 展示层级照淘宝

| 位置 | 显示 | 理由 |
|---|---|---|
| 商品卡 | `月销 N 件`；月销为 0 且累计 > 0 时退回 `已售 N 件` | 新品首月可能月销为 0，摆「月销 0 件」是劝退 |
| 商品详情购买区 | 先 `月销 N 件`，再 `累计已售 M 件` | 淘宝详情页也是「月销」在前、累计在后；月销为 0 时不显示累计前缀「累计已售」而写「已售」 |

月销与累计都为 0 → 两个都不显示，不占位。

### 5. 排序：月销优先，累计做 tiebreak

`sort=sold_count.desc` 先比 `monthly_sold_count`，相同再比 `sold_count`。

tiebreak 不是装饰：新品月销普遍是 0 或个位数，只比月销会出现大量并列，
排序结果在不同请求间抖动。加累计让并列档里也有稳定顺序。

接口排序与店面本地排序（未走服务端筛选时）用同一套比较规则。

## 后果

- order：`countSoldByVariantIds` / `countSoldByVariants` 加可选 `since`；
  新增 `MONTHLY_SOLD_DAYS` 与 `monthlySoldSince()` 并从模块入口导出
- API：列表与详情新增 `monthly_sold_count`；`sort=sold_count.desc` 改按月销排
- 店面：`CatalogProduct` / `StoreProduct` 新增 `monthlySoldCount`；
  商品卡、购买区、本地排序按上表调整
- 测试：order +3（两个口径分开取、`since` 原样透传、窗口边界是整数天）；
  api +2（详情两个字段互不覆盖、列表字段不缺）
- 无迁移（没有新数据，只是多一个查询条件）

## 遗留

- **窗口长度可配置**：现在写死 30 天。淘宝按品类不同（生鲜看 7 天、家具看 90 天），
  要做应放进店铺设置
- **月销缓存**：每次列表页都要跑两条聚合。数据量上来后应在 `order` 侧做日聚合表，
  而不是加缓存层
- **变体级月销**：接口只在变体上给了累计 `sold_count`，没给月销。
  购买区如果要做「这个尺码最近卖得好」需要补
